# Lab 03-04 - Azure App Service

**Objective:** Create and configure Azure App Service
**Estimated cost:** Medium - a Windows App Service plan on **B1**, scaled up to **S1** only for Parts 5 and
6, for about an hour in total. Plans bill per instance per hour, whether or not anyone uses the app. Also a
small storage account for one custom backup and an empty virtual network. Delete everything the same day.
**Licensing required:** None beyond an Azure subscription.

> **This lab has an hourly meter: the App Service plan.** Do it in one sitting. Teardown deletes the
> whole resource group.
>
> Parts 5 and 6 need **Standard**: deployment slots and autoscale don't exist in Basic. The lab scales up
> for those parts only.

Portal steps were checked against Microsoft Learn on 2026-09-30.

## Why this matters

A web app has to be reachable securely, scale with demand, survive mistakes and release new versions without downtime. In App Service, most of those features depend on the tier of the plan the app runs on.

## The desired state

When you finish, these will be true. Each one is checked in **Validation** below.

- A web app on a **Basic** plan, with **HTTPS only** and a **minimum TLS version** set.
- A **backup** configured, and **access restrictions** and **VNet integration** set.
- The plan scaled up to **Standard**, a **staging slot**, a swap, and an **autoscale** rule.

## Prerequisites

- **Contributor** or **Owner** on the lab subscription.
- The Azure CLI, and PowerShell for building two tiny site packages.

```powershell
$LabId = '03-04'
$Rg    = "rg-az104-lab-$LabId"
$Loc   = '<region>'
$n     = Get-Random -Maximum 99999
$Plan  = 'asp-az104-0304'
$App   = "app-az104-0304-$n"            # globally unique: becomes $App.azurewebsites.net
az group create --name $Rg --location $Loc --tags az104-module=$LabId

# Two one-page sites, so a slot swap is visible
foreach ($v in 'v1','v2') {
  New-Item -ItemType Directory "$env:TEMP\site-$v" -Force | Out-Null
  "<h1>AZ-104 lab 03-04 - $v</h1>" | Set-Content "$env:TEMP\site-$v\index.html"
  Compress-Archive -Path "$env:TEMP\site-$v\*" -DestinationPath "$env:TEMP\site-$v.zip" -Force
}
```

## Part 1 - A Basic plan and an app

```powershell
az appservice plan create --name $Plan --resource-group $Rg --sku B1 --tags az104-module=$LabId
az webapp create --name $App --resource-group $Rg --plan $Plan --tags az104-module=$LabId
az webapp deploy --name $App --resource-group $Rg --src-path "$env:TEMP\site-v1.zip" --type zip

"https://$App.azurewebsites.net"        # open it: "v1"
```

If your CLI version asks for a runtime stack, add `--runtime` with a Windows value from
`az webapp list-runtimes --os windows`. Any stack serves a static `index.html`.

The plan is a Windows plan (the default) on one B1 instance. In the portal, open the **plan** and note
**Apps** (one) and **Scale out** (manual only, maximum 3 in Basic). Then open the app >
**Deployment slots**. Basic shows that slots need a higher tier.

## Part 2 - TLS settings, and the custom domain walkthrough

```powershell
az webapp update     --name $App --resource-group $Rg --https-only true
az webapp config set --name $App --resource-group $Rg --min-tls-version 1.2
```

Browse to `http://$App.azurewebsites.net`: you're redirected to HTTPS. The default `azurewebsites.net` name
already has a certificate.

**Custom domain (walkthrough, or hands-on if you own a domain):**

1. App > **Custom domains** > **Add custom domain**. Read the two records the dialog asks for: a **CNAME**
   (`www` → `$App.azurewebsites.net`) or an **A** record for a root domain, **plus** a **TXT** `asuid`
   record with the domain verification ID.
2. If you own a domain, create both records at your DNS provider, **Validate**, and add the domain.
3. Then **Add binding** > **Create App Service Managed Certificate** > **SNI SSL**. The managed certificate
   is free and renews itself, but it can't be a wildcard or be exported.

Without a domain, stop at step 1. Microsoft's walkthrough in the lesson's Sources covers the rest.

## Part 3 - Backups

**Automatic backups** exist with no configuration in Basic and higher. Open **Backups**: they run hourly and
are kept for 30 days. A brand-new app may not show one yet.

**A custom backup** needs a storage account:

```powershell
$Sa = "az104lab0304$n"
az storage account create --name $Sa --resource-group $Rg --location $Loc --sku Standard_LRS --kind StorageV2 --tags az104-module=$LabId
```

App > **Backups** > **Configure custom backups**. Pick `$Sa`, create a container `backups`, **Configure**, then
**Backup Now**. When it completes, open the container in the storage account: the backup is a `.zip` plus an
`.xml` file you could download. That's a custom-backup feature; automatic backups aren't downloadable.

## Part 4 - Networking: inbound restrictions, outbound integration

**Access restrictions (inbound):**

```powershell
# One allow rule for a range that isn't yours
az webapp config access-restriction add --name $App --resource-group $Rg `
  --rule-name not-me --action Allow --ip-address 203.0.113.0/24 --priority 100
```

Browse to the app: **403 Forbidden**. One allow rule switched the unmatched action to **deny**. Now open
**Networking** > **Access restriction** and look at the **Advanced tool site** tab: it has its own rules,
still unrestricted. Remove the rule:

```powershell
az webapp config access-restriction remove --name $App --resource-group $Rg --rule-name not-me
```

**VNet integration (outbound):**

```powershell
az network vnet create --name vnet-az104-0304 --resource-group $Rg --address-prefix 10.34.0.0/16 `
  --subnet-name apps --subnet-prefixes 10.34.1.0/24
az network vnet subnet update --name apps --vnet-name vnet-az104-0304 --resource-group $Rg `
  --delegations Microsoft.Web/serverFarms
az webapp vnet-integration add --name $App --resource-group $Rg --vnet vnet-az104-0304 --subnet apps
```

The app can now **call** resources in that virtual network. It isn't any more **reachable** from it: inbound
private access would take a private endpoint.

## Part 5 - Scale up to Standard, then deployment slots

```powershell
az appservice plan update --name $Plan --resource-group $Rg --sku S1      # the meter goes up now

az webapp deployment slot create --name $App --resource-group $Rg --slot staging
az webapp deploy --name $App --resource-group $Rg --slot staging --src-path "$env:TEMP\site-v2.zip" --type zip

# One setting that travels with the code, one that stays with its slot
az webapp config appsettings set --name $App --resource-group $Rg --settings FEATURE_X=off
az webapp config appsettings set --name $App --resource-group $Rg --slot staging --settings FEATURE_X=on
az webapp config appsettings set --name $App --resource-group $Rg               --slot-settings DB=prod-db
az webapp config appsettings set --name $App --resource-group $Rg --slot staging --slot-settings DB=staging-db
```

Production shows **v1**; `https://$App-staging.azurewebsites.net` shows **v2**. **Predict** both apps' settings
after a swap, then swap **with preview**:

```powershell
az webapp deployment slot swap --name $App --resource-group $Rg --slot staging --target-slot production --action preview
# Phase 1 done: staging now runs with production's sticky settings. Check staging, then complete:
az webapp deployment slot swap --name $App --resource-group $Rg --slot staging --target-slot production --action swap

az webapp config appsettings list --name $App --resource-group $Rg --query "[?name=='FEATURE_X' || name=='DB'].{name:name, value:value}" -o table
```

Production now shows **v2**, with `FEATURE_X=on` (it travelled) and `DB=prod-db` (sticky). Roll back by
running the same swap again.

## Part 6 - Autoscale (Standard and higher)

```powershell
$planId = az appservice plan show --name $Plan --resource-group $Rg --query id -o tsv
az monitor autoscale create --resource-group $Rg --resource $planId --name autoscale-0304 `
  --min-count 1 --max-count 2 --count 1
az monitor autoscale rule create --resource-group $Rg --autoscale-name autoscale-0304 `
  --condition "CpuPercentage > 70 avg 10m" --scale out 1
az monitor autoscale rule create --resource-group $Rg --autoscale-name autoscale-0304 `
  --condition "CpuPercentage < 30 avg 10m" --scale in 1
```

Open the plan > **Scale out (App Service plan)**: **Rules Based** with your two rules, between 1 and 2
instances. The same engine as scale sets (03-02): scale-in needs every scale-in rule to agree. Note the
**Automatic** option: it's for Premium v2 and higher.

## What just happened?

The app never owned its compute: the **App Service plan** did, and every app on the plan shared it. That's why scaling, slots and autoscale were plan decisions, and why some features only appeared after you scaled up to Standard. Access restrictions controlled traffic **into** the app; VNet integration controlled traffic **out** of it. They're separate settings for separate directions.

## Teardown

### 1. Resources

```powershell
az group delete --name $Rg --yes
Remove-Item "$env:TEMP\site-v1*","$env:TEMP\site-v2*" -Recurse -ErrorAction SilentlyContinue
```

This removes the plan (and its meter), the app and its slot, the autoscale setting, the storage account
holding the backup, and the virtual network.

### 2. Subscription scope

None.

### 3. Directory scope

None.

### 4. Soft-deleted remains

None from this lab.

### 5. Access

Remove any role you added to your working account only for this lab. If you mapped a real domain in Part 2,
delete its CNAME and TXT records at your DNS provider. A CNAME left pointing at a deleted
`azurewebsites.net` name is how subdomain takeover happens.

### 6. Verify

```powershell
az group exists --name $Rg                                                               # false
az appservice plan list --query "[?contains(name,'az104-0304')].name" -o tsv              # nothing
```

Tick these once the commands above return what's expected. The lab counts as **practised** only when the validation and teardown checklists are both complete.

- [ ] `az group exists` for the lab resource group returns **false**.
- [ ] No App Service plan named `*az104-0304*` remains.
