# Lab 03-02 - Virtual Machines

**Objective:** Create and configure virtual machines
**Estimated cost:** Medium - one small B-series Linux VM (no public IP) with a Standard SSD OS disk and
a small data disk. It runs for roughly an hour in total and is deallocated between parts. The scale set
has **zero instances**, so it bills no VM compute. The disks bill until teardown even while the VM is
deallocated. Delete everything the same day.
**Licensing required:** None beyond an Azure subscription.

> **This lab has an hourly meter.** Complete **Module 0** first, so the budget and the compute brake
> exist. Every VM here is tagged `az104-module = 03-02`, which is the tag the brake deallocates.
>
> Do the lab in one sitting. If you have to stop, **deallocate** the VM (`az vm deallocate`); stopping
> it from inside Linux keeps billing for compute.

Portal steps were checked against Microsoft Learn on 2026-09-30.

## Prerequisites

- **Contributor** or **Owner** on the lab subscription.
- The Azure CLI, and a region with availability zones.

```powershell
$LabId = '03-02'
$Rg    = "rg-az104-lab-$LabId"
$Rg2   = "rg-az104-lab-$LabId-moved"
$Loc   = '<region-with-zones>'
$Vm    = 'vm-az104-0302'
az login
az group create --name $Rg  --location $Loc --tags az104-module=$LabId
az group create --name $Rg2 --location $Loc --tags az104-module=$LabId

# Pick the smallest B-series size offered in your region and zone 1
az vm list-skus --location $Loc --size Standard_B --zone --query "[].name" -o tsv
$Size  = '<a-small-B-series-size>'      # for example Standard_B1s, if listed
```

## Part 0 - Register encryption at host (one-time, free)

```powershell
az feature register --namespace Microsoft.Compute --name EncryptionAtHost
az feature show     --namespace Microsoft.Compute --name EncryptionAtHost --query properties.state -o tsv
# Wait until it says Registered (a few minutes), then:
az provider register --namespace Microsoft.Compute
```

Registration changes nothing about existing VMs. It only allows the setting to be used.

## Part 1 - Create a zonal VM with encryption at host

```powershell
az vm create --resource-group $Rg --name $Vm --image Ubuntu2204 --size $Size `
  --zone 1 --encryption-at-host true `
  --admin-username azureuser --generate-ssh-keys `
  --public-ip-address '""' --nsg '""' `
  --storage-sku StandardSSD_LRS --tags az104-module=$LabId

az vm show --resource-group $Rg --name $Vm `
  --query "{size:hardwareProfile.vmSize, zone:zones[0], encryptionAtHost:securityProfile.encryptionAtHost}" -o table
```

In the portal, open the VM and list what `az vm create` made: the VM, an OS **disk**, a **network
interface** and a **virtual network**. Each is a separate resource. Then open **Size**: the zone and the
availability option are fixed now, and there's no way to put this VM in an availability set.

> If you skip `--public-ip-address '""'` and `--nsg '""'`, the CLI creates a public IP and an NSG, and a
> Standard public IP bills while it exists. The quoting shown passes an empty string from PowerShell.

## Part 2 - Disks

```powershell
# Attach a new 4 GiB Standard SSD data disk while the VM runs
az vm disk attach --resource-group $Rg --vm-name $Vm --name "$Vm-data" --new --size-gb 4 --sku StandardSSD_LRS

# Expand the data disk ONLINE: data disks can grow without deallocating
az disk update --resource-group $Rg --name "$Vm-data" --size-gb 8
az disk show   --resource-group $Rg --name "$Vm-data" --query diskSizeGB

# Try to shrink it back: this fails, because managed disks can't shrink
az disk update --resource-group $Rg --name "$Vm-data" --size-gb 4
```

Now **change the disk type**, which needs the VM stopped:

```powershell
az disk update --resource-group $Rg --name "$Vm-data" --sku Standard_LRS     # refused while the VM runs
az vm deallocate --resource-group $Rg --name $Vm
az disk update --resource-group $Rg --name "$Vm-data" --sku Standard_LRS     # succeeds; the conversion is instant
```

Leave the VM **deallocated** for Part 3.

## Part 3 - Sizes

```powershell
az vm get-instance-view --resource-group $Rg --name $Vm --query "instanceView.statuses[1].displayStatus"   # VM deallocated

# Deallocated, the VM can be resized to any size the region and zone offer
az vm list-vm-resize-options --resource-group $Rg --name $Vm --query "[?starts_with(name,'Standard_B')].name" -o tsv
az vm resize --resource-group $Rg --name $Vm --size '<another-small-B-series-size>'
az vm start  --resource-group $Rg --name $Vm
```

Then resize **while running** to a size that `list-vm-resize-options` returns. The VM **restarts**:
watch **Activity log** for the restart. A size that isn't in the running VM's list would require
deallocating first.

## Part 4 - Encryption at host on an existing VM

The VM already has it. To see the rule for an existing VM, turn it **off** while running:

```powershell
az vm update --resource-group $Rg --name $Vm --set securityProfile.encryptionAtHost=false   # refused while running
az vm deallocate --resource-group $Rg --name $Vm
az vm update --resource-group $Rg --name $Vm --set securityProfile.encryptionAtHost=false   # succeeds when deallocated
az vm update --resource-group $Rg --name $Vm --set securityProfile.encryptionAtHost=true
```

Leave it **deallocated**. The remaining parts don't need it running.

## Part 5 - Move the VM to another resource group

A VM moves **with** its disks and network interface. Collect their IDs:

```powershell
$ids = @(
  (az vm show   -g $Rg -n $Vm --query id -o tsv),
  (az vm show   -g $Rg -n $Vm --query storageProfile.osDisk.managedDisk.id -o tsv),
  (az disk show -g $Rg -n "$Vm-data" --query id -o tsv),
  (az vm show   -g $Rg -n $Vm --query "networkProfile.networkInterfaces[0].id" -o tsv)
)
az resource move --destination-group $Rg2 --ids $ids
az vm show -g $Rg2 -n $Vm --query id -o tsv     # the resource ID now contains the new resource group
```

The virtual network stays in the original resource group; the NIC can reference it across resource groups.
A VM can't be moved to a **different virtual network**: that means re-creating it.

**Region move, walkthrough:** open **Azure Resource Mover** > **Move across regions**. Read the steps:
select the source and target regions, add the VM, and let Resource Mover add its dependencies.
**Don't start a move.**

## Part 6 - An availability set (free, no VMs)

```powershell
az vm availability-set create --resource-group $Rg --name avset-az104-0302 `
  --platform-fault-domain-count 2 --platform-update-domain-count 5
az vm availability-set list-sizes --resource-group $Rg --name avset-az104-0302 --query "[0:5].name" -o tsv
```

Open the VM's **Overview**. There's no option to add it to `avset-az104-0302`: an existing VM can't join
an availability set. Open the availability set: its fault and update domain counts can't be changed
either.

## Part 7 - A scale set with zero instances, and autoscale

**Portal:** **Virtual machine scale sets** > **Create**:

1. Resource group `rg-az104-lab-03-02`, name `vmss-az104-0302`, your region, **availability zones** 1, 2, 3.
2. **Orchestration mode: Flexible**. Note the notice that this choice can't be changed later.
3. Image **Ubuntu Server 22.04 LTS**, your small B-series size, SSH key authentication.
4. **Scaling: initial instance count 0.**
5. Networking: **no** public IP per instance, and **no** load balancer.
6. Tag `az104-module = 03-02`, then **Review + create**.

Then the autoscale profile and rules:

```powershell
az monitor autoscale create --resource-group $Rg --resource vmss-az104-0302 `
  --resource-type Microsoft.Compute/virtualMachineScaleSets --name autoscale --min-count 0 --max-count 2 --count 0
az monitor autoscale rule create --resource-group $Rg --autoscale-name autoscale `
  --condition "Percentage CPU > 70 avg 10m" --scale out 1
az monitor autoscale rule create --resource-group $Rg --autoscale-name autoscale `
  --condition "Percentage CPU < 30 avg 10m" --scale in 1
az monitor autoscale show --resource-group $Rg --name autoscale --query "profiles[0].capacity"
```

Open the scale set > **Scaling**. Read the instance limits and both rules, including the **duration** and
**cooldown** of each. With minimum 0 and no instances, nothing runs and nothing bills for compute.

## Validation

```powershell
az vm show -g $Rg2 -n $Vm --query "{rg:resourceGroup, zone:zones[0], eah:securityProfile.encryptionAtHost}" -o table
az disk show -g $Rg2 -n "$Vm-data" --query "{size:diskSizeGB, sku:sku.name}" -o table      # 8, Standard_LRS
az vmss show -g $Rg -n vmss-az104-0302 --query "{mode:orchestrationMode, capacity:sku.capacity}" -o table
```

## Teardown

### 1. Resources

```powershell
az group delete --name $Rg2 --yes      # the VM, its disks and NIC
az group delete --name $Rg  --yes      # the VNet, availability set, scale set and autoscale setting
```

Deleting the VM alone would **leave its disks billing**. Deleting the resource groups removes everything.

### 2. Subscription scope

The `EncryptionAtHost` feature registration stays on the subscription. It costs nothing and changes
nothing until a VM uses it. Leave it, or unregister it with `az feature unregister`.

### 3. Directory scope

None.

### 4. Soft-deleted remains

None.

### 5. Access

Remove any role you added to your working account only for this lab. The SSH key that
`--generate-ssh-keys` created stays in your local `.ssh` folder. Delete it if you don't need it.

### 6. Verify

```powershell
az group exists --name $Rg ; az group exists --name $Rg2                            # false, false
az vm list --query "[?tags.\"az104-module\"=='03-02'].name" -o tsv                 # nothing
az disk list --query "[?contains(name,'az104-0302')].name" -o tsv                  # nothing
```

Then mark teardown as confirmed in the Academy.
