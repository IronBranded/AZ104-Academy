# Lab 03-01 - ARM Templates and Bicep

**Objective:** Automate deployment of resources by using Azure Resource Manager (ARM) templates or Bicep files
**Estimated cost:** Low - one Standard LRS storage account, empty or holding a container, deleted the
same day. What-if, export and decompile cost nothing.
**Licensing required:** None beyond an Azure subscription.

> Complete **01-03** first. All the templates for this lab are in
> [`labs/03-compute/templates/`](./templates/). They and their solutions are compiled and linted in CI
> (`tools/check-templates.sh`), so if a step fails, the cause is your change or your environment, not
> the starting file.

Portal steps were checked against Microsoft Learn on 2026-09-30.

## Why this matters

Creating resources by hand is slow, hard to repeat and easy to get slightly wrong. A template writes the deployment down, so it can be reviewed, repeated and deployed the same way every time.

## The desired state

When you finish, these will be true. Each one is checked in **Validation** below.

- A storage account deployed from a **Bicep** file, after a **what-if** preview.
- A **parameter** added to the Bicep file and to the ARM template, and both redeployed.
- A **complete mode** deployment previewed, so you can see what it would delete, and not run.
- A deployment **exported** to JSON and **decompiled** to Bicep.

## Part 1 - Interpret

Open [`storage.json`](./templates/storage.json) and [`storage.bicep`](./templates/storage.bicep) side by
side. **Answer from the files, before deploying anything:**

1. How many resources does each deploy?
2. If you pass no parameters, where do the location and SKU come from?
3. Which values can `skuName` take, and where is that enforced in each file?
4. What does `uniqueString(resourceGroup().id)` guarantee about the account name if you deploy twice
   to the same resource group? And to a different resource group?
5. The JSON output `blobEndpoint` uses `reference(resourceId(...))`. What does the Bicep file use
   instead?

Then compile the Bicep file and compare the result with the hand-written JSON:

```powershell
az bicep build --file storage.bicep --outfile ./built.json
```

The two differ in syntax, `format()` versus `concat()` for example, but deploy the same thing.

## Part 2 - Deploy, with a preview first

```powershell
# Preview: every change is shown, nothing is made
az deployment group what-if --resource-group $Rg --parameters storage.bicepparam

# Deploy the Bicep file through its .bicepparam file (the 'using' line names the Bicep file)
az deployment group create --resource-group $Rg --name deploy-bicep --parameters storage.bicepparam

# Deploy the ARM JSON version too. Same resource group, same uniqueString, so the same account.
az deployment group what-if --resource-group $Rg --template-file storage.json --parameters '@storage.parameters.json'
```

The second what-if targets the **same** storage account: same resource group, same `uniqueString`.
Expect **NoChange**, or a few properties listed as changing. Microsoft notes that what-if can report
properties the service sets by default as changes ("noise"). It's the same resource, whichever
language described it.

Open the resource group > **Deployments** > `deploy-bicep`. Look at **Inputs**, **Outputs** and
**Template**. The template stored is **JSON**: Resource Manager never saw the Bicep file.

## Part 3 - Modify the Bicep file

Edit `storage.bicep`:

1. Allow `'Standard_ZRS'` in `skuName`.
2. Add a `containerName` parameter defaulting to `'reports'`.
3. Add a blob service and a container **using `parent:`**, with no `dependsOn`.
4. Add an output with the container's resource ID.

```powershell
az bicep build --file storage.bicep --stdout | Select-String -Pattern 'dependsOn' -Context 0,2
```

The compiled JSON **contains `dependsOn` entries you never wrote**: Bicep derived them from `parent:`.
Compare your file with [`solutions/storage-modified.bicep`](./templates/solutions/storage-modified.bicep),
then preview and deploy:

```powershell
az deployment group what-if --resource-group $Rg --template-file storage.bicep
az deployment group create  --resource-group $Rg --name deploy-container --template-file storage.bicep
```

What-if lists the blob service and container as **Create** and the storage account as **NoChange**, or as
**Modify** if you changed something about it.

## Part 4 - Modify the ARM template

Make the same change in `storage.json`:

1. Add `"Standard_ZRS"` to `allowedValues`.
2. Add a `containerName` parameter.
3. Add a `Microsoft.Storage/storageAccounts/blobServices/containers` resource. Name it
   `"[format('{0}/default/{1}', variables('storageName'), parameters('containerName'))]"`, and give it
   a `dependsOn` on the storage account's `resourceId(...)`.

Check it against [`solutions/storage-modified.json`](./templates/solutions/storage-modified.json), then
**preview** it:

```powershell
az deployment group what-if --resource-group $Rg --template-file storage.json --parameters '@storage.parameters.json'
```

Try deleting the `dependsOn` and running what-if again. A missing dependency is a **timing** problem:
Resource Manager may create the container before its account exists, so it shows up at deployment
time, not necessarily in a preview. Put it back.

## Part 5 - Complete mode, previewed and not run

Create something the template doesn't know about, then ask what complete mode would do:

```powershell
az network vnet create --resource-group $Rg --name vnet-not-in-template --address-prefix 10.31.0.0/16
az deployment group what-if --resource-group $Rg --template-file storage.bicep --mode Complete
```

What-if lists `vnet-not-in-template` as **Delete**. **Don't deploy it.** Now add a Delete lock and preview
again:

```powershell
az lock create --name no-delete --lock-type CanNotDelete --resource-group $Rg
az deployment group what-if --resource-group $Rg --template-file storage.bicep --mode Complete
az lock delete --name no-delete --resource-group $Rg
```

Read what-if's output with the lock in place. Microsoft documents that complete mode doesn't delete
resources in a locked resource group; what-if is only a preview. Remove the lock before continuing.

## Part 6 - Export and decompile

**Export the current state:**

1. Portal: the resource group > **Export template**. Compare the **ARM Template** and **Bicep** tabs.
   Bicep export is available **only in the portal**. Note what's missing or needs parameterizing: names
   are hard-coded, and some API versions may be older than the ones you wrote.
2. CLI:

```powershell
az group export --name $Rg > exported.json
az bicep decompile --file exported.json
```

**Get the exact template a deployment used:** **Deployments** > `deploy-container` > **Template**. This is
what was deployed, not a reconstruction of the current state.

**Decompile the hand-written ARM template** and compare it with the hand-written Bicep solution:

```powershell
Copy-Item solutions/storage-modified.json ./to-decompile.json
az bicep decompile --file to-decompile.json
az bicep lint --file to-decompile.bicep
```

Find the four differences from `solutions/storage-modified.bicep`:

1. The linter warns **`prefer-interpolation`**: the decompiler kept `concat()`.
2. The container's **symbolic name** is generated from the JSON name, something like
   `storageName_default_container`.
3. The container is named with a **slash path** instead of using `parent:`.
4. It keeps an **explicit `dependsOn`** that `parent:` would have made unnecessary.

The decompiled file deploys the same thing; it just isn't how you'd write it. That's what best-effort
means.

## What just happened?

Every deployment was a request to **Azure Resource Manager**, the same service the portal uses. Bicep was compiled to ARM JSON before Resource Manager saw it. **What-if** showed the change before it happened, and the complete-mode preview showed why complete mode is dangerous: anything in the resource group that isn't in the template is deleted.
