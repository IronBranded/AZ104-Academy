# Lab 05-01 - Monitoring Resources in Azure

**Objective:** Monitor resources in Azure
**Estimated cost:** Medium - one small B-series Linux VM with a Standard public IP (used for outbound tests; no
inbound port is opened) for about 90 minutes, a Log Analytics workspace ingesting a little data, a small storage
account, one metric alert rule and one connection monitor. Delete everything the same day.
**Licensing required:** None beyond an Azure subscription.

> Complete **03-02** and **04-02** first. **Three things this lab creates live outside its resource group**: the
> subscription's activity-log diagnostic setting, the **connection monitor** (it belongs to the regional Network
> Watcher in `NetworkWatcherRG`) and, possibly, the VM insights **data collection rule**. Teardown removes each one
> explicitly.

Portal steps were checked against Microsoft Learn on 2026-10-01.

## Prerequisites

- **Owner** or **Contributor** on the lab subscription, plus permission to create subscription diagnostic settings
  (Owner, or Monitoring Contributor).
- The Azure CLI, and an email address you can read for the alert.

```powershell
$LabId = '05-01'
$Rg    = "rg-az104-lab-$LabId"
$Loc   = '<region>'
$n     = Get-Random -Maximum 99999
$Sa    = "az104lab0501$n"
$Email = '<your-email-address>'
az group create --name $Rg --location $Loc --tags az104-module=$LabId

az monitor log-analytics workspace create --resource-group $Rg --workspace-name law-az104-0501 --location $Loc
$lawId = az monitor log-analytics workspace show -g $Rg -n law-az104-0501 --query id -o tsv
```

## Part 1 - Log settings: activity log and resource logs

```powershell
# The subscription's activity log, to the workspace (no ingestion charge for activity log data)
az monitor diagnostic-settings subscription create --name az104-0501-activity --location $Loc `
  --workspace $lawId --logs '[{\"category\":\"Administrative\",\"enabled\":true}]'

# A storage account, and its blob logs to the workspace. Resource logs aren't collected without this.
az storage account create --name $Sa --resource-group $Rg --location $Loc --sku Standard_LRS --kind StorageV2
$blobSvc = (az storage account show -n $Sa -g $Rg --query id -o tsv) + '/blobServices/default'
az monitor diagnostic-settings create --name blob-to-law --resource $blobSvc --workspace $lawId `
  --logs '[{\"categoryGroup\":\"allLogs\",\"enabled\":true}]'
```

Create some blob traffic, so there's something to measure and log:

```powershell
$key = az storage account keys list -n $Sa -g $Rg --query "[0].value" -o tsv
az storage container create --name lab --account-name $Sa --account-key $key | Out-Null
1..20 | ForEach-Object { "line $_" | Set-Content "$env:TEMP\f$_.txt"; az storage blob upload --container-name lab --name "f$_.txt" --file "$env:TEMP\f$_.txt" --account-name $Sa --account-key $key --overwrite | Out-Null }
az storage blob list --container-name lab --account-name $Sa --account-key $key -o table | Out-Null
```

> PowerShell 7 passes the JSON above as written. If your shell mangles the quotes, use the portal (**Diagnostic
> settings** > **Add**) instead.

## Part 2 - A VM, and VM insights

```powershell
az vm create --resource-group $Rg --name vm-az104-0501 --image Ubuntu2204 --size '<a-small-B-series-size>' `
  --public-ip-sku Standard --nsg '""' --admin-username azureuser --generate-ssh-keys --tags az104-module=$LabId
```

The Standard public IP gives the VM **outbound** access for Part 6. With no NSG rule allowing it, **inbound** stays
closed: Standard public IPs are secure by default.

**Enable VM insights in the portal:** **Monitor** > **Virtual Machines** > **Not monitored** > `vm-az104-0501` >
**Enable**. Choose **Azure Monitor agent**, your workspace `law-az104-0501`, and **don't** enable processes and
dependencies (the Map retires in 2028). Note the **data collection rule** it creates, prefixed `MSVMI-`, and **which
resource group** it goes into. Teardown needs that.

## Part 3 - Interpret metrics

1. **Storage account** > **Metrics**: metric **Transactions**, aggregation **Sum**. Then **Apply splitting** by
   **API name**: one line per operation type (PutBlob, ListBlobs…). Splitting works because the metric has dimensions.
2. **VM** > **Metrics**: **Percentage CPU**, aggregation **Average**: a host (platform) metric, collected with no agent.
   Free space on each logical disk is a **guest** counter: it arrives only through the Azure Monitor Agent, here via
   VM insights.
3. Set the time range to the last 90 days: one chart shows at most 30, of the 93 days kept.
4. **Monitor** > **Insights** > **Storage accounts**: capacity, transactions and availability for every storage account,
   with no setup.

## Part 4 - An alert rule, an action group, and an alert processing rule

```powershell
az monitor action-group create --resource-group $Rg --name ag-az104-0501 --short-name az104lab `
  --action email me $Email

$vmId = az vm show -g $Rg -n vm-az104-0501 --query id -o tsv
az monitor metrics alert create --resource-group $Rg --name cpu-over-50 --scopes $vmId `
  --condition "avg Percentage CPU > 50" --window-size 5m --evaluation-frequency 1m `
  --severity 2 --action ag-az104-0501 --description "AZ-104 lab 05-01"
```

Generate CPU load for 10 minutes. This is a shell loop, so no package is needed:

```powershell
az vm run-command invoke -g $Rg -n vm-az104-0501 --command-id RunShellScript --no-wait `
  --scripts "timeout 600 sh -c 'while :; do :; done' & timeout 600 sh -c 'while :; do :; done' &"
```

Within a few minutes the alert **fires**: **Monitor** > **Alerts** shows it, and the email arrives. When the load ends,
the alert **resolves** if the rule's **automatically resolve** setting is on (Validation shows it as `autoMitigate`).
That makes the alert **stateful**, and a resolution email follows.

Now add an **alert processing rule** that suppresses notifications for the resource group, as during maintenance:

```powershell
az monitor alert-processing-rule create --resource-group $Rg --name maintenance-0501 `
  --scopes "/subscriptions/$((az account show --query id -o tsv))/resourceGroups/$Rg" `
  --rule-type RemoveAllActionGroups --description "Maintenance window"
```

Run the CPU load again. The alert **fires and appears in Monitor > Alerts**, but **no email** arrives. Suppression removes
the action groups; it doesn't stop the alert. Open the alert rule processing page and note the schedule options:
always, once, or recurring.

## Part 5 - Query logs with KQL

**Monitor** > **Logs**, scope `law-az104-0501`. Data can take several minutes to arrive.

```kusto
// What happened in this subscription today, by operation
AzureActivity
| where TimeGenerated > ago(1d)
| summarize Count = count() by OperationNameValue
| order by Count desc

// Blob operations from the resource logs you enabled in Part 1
StorageBlobLogs
| where TimeGenerated > ago(1h)
| summarize Requests = count() by OperationName, StatusText

// VM insights: guest CPU in 1-minute bins during the load test
InsightsMetrics
| where Namespace == "Processor" and Name == "UtilizationPercentage"
| summarize AvgCpu = avg(Val) by bin(TimeGenerated, 1m), Computer
| render timechart

// Agent check-ins
Heartbeat
| summarize LastSeen = max(TimeGenerated) by Computer
```

## Part 6 - Network Watcher and Connection monitor

**Network Watcher** > **Connection monitor** > **Create**:

1. Name `cm-az104-0501`, your region. Note the **Network Watcher** it attaches to, in **`NetworkWatcherRG`**.
2. **Test group** `outbound`: **source** `vm-az104-0501` (the portal installs the **Network Watcher agent extension**).
   **Destinations**: the external address `learn.microsoft.com`, and your storage account's blob endpoint
   `<account>.blob.core.windows.net`.
3. **Test configuration**: **HTTP**, port 443, every 30 seconds. Create.

After a few minutes, the monitor shows **% checks failed** (near 0) and **round-trip time** for each test. Now break it
with an NSG on the VM's NIC that denies outbound 443:

```powershell
az network nsg create -g $Rg -n nsg-0501
az network nsg rule create -g $Rg --nsg-name nsg-0501 -n deny-443-out --priority 100 --direction Outbound `
  --access Deny --protocol Tcp --destination-port-ranges 443
$nic = (az vm show -g $Rg -n vm-az104-0501 --query "networkProfile.networkInterfaces[0].id" -o tsv).Split('/')[-1]
az network nic update -g $Rg -n $nic --network-security-group nsg-0501
```

Within a few test cycles, **% checks failed** rises to 100 for both destinations. Open a failing test and look for the
blocking component: Connection monitor can identify the **NSG rule** responsible. Remove the NSG association, and watch the tests recover:

```powershell
az network nic update -g $Rg -n $nic --remove networkSecurityGroup
```

Then open **Network Watcher** > **Topology** for the lab resource group: the VNet, subnet, VM and NIC as a diagram, with no
agent involved.

Deallocate the VM as soon as you've seen the recovery:

```powershell
az vm deallocate -g $Rg -n vm-az104-0501
```

## Validation

```powershell

az monitor metrics alert show -g $Rg -n cpu-over-50 --query "{enabled:enabled, autoMitigate:autoMitigate}" -o table
az monitor alert-processing-rule list -g $Rg -o table

```

## Teardown

### 1. Resources

**The connection monitor first.** It lives under the regional Network Watcher, not in your resource group:

```powershell
az network watcher connection-monitor delete --location $Loc --name cm-az104-0501
az group delete --name $Rg --yes
Remove-Item "$env:TEMP\f*.txt" -ErrorAction SilentlyContinue
```

The resource group deletion removes the VM, workspace, storage account, action group, alert rule and alert processing rule.

### 2. Subscription scope

The activity log diagnostic setting is a **subscription** setting:

```powershell
az monitor diagnostic-settings subscription delete --name az104-0501-activity --yes
```

Then the VM insights **data collection rule**, if it was created outside the lab resource group:

```powershell
az monitor data-collection rule list --query "[?starts_with(name,'MSVMI-')].{name:name, rg:resourceGroup}" -o table
# az monitor data-collection rule delete --name <name> --resource-group <rg> --yes
```

Delete only the rule this lab created. Another VM may share one.

### 3. Directory scope

None.

### 4. Soft-deleted remains

The deleted Log Analytics workspace can remain **soft-deleted for up to 14 days** (00-02). Re-creating one with the same
name in the same resource group and region in that window recovers it. **Network Watcher** and **NetworkWatcherRG** stay:
they're free, shared by the whole region, and created automatically again if removed.

### 5. Access

Remove any role you added to your working account only for this lab.

### 6. Verify

```powershell
az group exists --name $Rg                                                                  # false
az network watcher connection-monitor list --location $Loc --query "[?name=='cm-az104-0501']" -o tsv   # nothing
az monitor diagnostic-settings subscription list --query "value[?name=='az104-0501-activity']" -o tsv   # nothing
```

Then mark teardown as confirmed in the Academy.
