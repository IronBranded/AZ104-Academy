# Lab 05-02 - Backup and Recovery

**Objective:** Implement backup and recovery
**Estimated cost:** High - a small B-series VM running for several hours (the first backup and the initial Site
Recovery replication both take time), backup storage, Site Recovery replica disks and a cache storage account, a
test-failover VM in a second region for a few minutes, and a Log Analytics workspace. This is the most expensive lab
in the Academy. **Follow the teardown order exactly**: done in the wrong order, soft delete keeps the vault, and its
charges, for 14 days.
**Licensing required:** None beyond an Azure subscription.

> Complete **03-02** and **05-01** first. Plan for an afternoon: you start the long-running steps (first backup,
> initial replication) early and work on other parts while they run.
>
> **The rule that matters most:** in teardown you **disable soft delete before deleting backup data**. That one step
> decides whether the vault can be deleted today or in two weeks.

Portal steps were checked against Microsoft Learn on 2026-10-01.

## Prerequisites

- **Owner** or **Contributor** on the lab subscription.
- The Azure CLI, and an email address for alert notifications.
- Two regions: your usual one (`$Loc`) and another for disaster recovery (`$DrLoc`). The Site Recovery portal offers
  the target regions available to you.

```powershell
$LabId = '05-02'
$Rg    = "rg-az104-lab-$LabId"
$Loc   = '<region>'
$DrLoc = '<another-region>'
$Email = '<your-email-address>'
az group create --name $Rg --location $Loc --tags az104-module=$LabId

az vm create --resource-group $Rg --name vm-az104-0502 --image Ubuntu2204 --size '<a-small-B-series-size>' `
  --public-ip-address '""' --nsg '""' --admin-username azureuser --generate-ssh-keys --tags az104-module=$LabId
```

## Part 1 - Two vaults, and the redundancy decision

```powershell
az backup vault create --resource-group $Rg --name rsv-az104-0502 --location $Loc
az backup vault backup-properties show --resource-group $Rg --name rsv-az104-0502 -o json
```

In the output, find the storage redundancy (geo-redundant) and the soft delete state (enabled): the defaults are
**GRS** and soft delete **on**. For a lab, LRS is cheaper. Change it **now**: once the
vault protects its first item, redundancy is locked.

```powershell
az backup vault backup-properties set --resource-group $Rg --name rsv-az104-0502 --backup-storage-redundancy LocallyRedundant
```

**A Backup vault:** in the portal, **Backup vaults** > **Create**, named `bv-az104-0502`, in `$Loc` and the lab
resource group. Then open **Backup** on it and look at the datasource types offered: disks, blobs, PostgreSQL… but
**no virtual machines**. Those belong to the Recovery Services vault. Leave the Backup vault empty.

## Part 2 - Policies, protection and the first backup

Look at the default policy, then protect the VM with it:

```powershell
az backup policy show --resource-group $Rg --vault-name rsv-az104-0502 --name DefaultPolicy -o json
# Read: the schedule (daily), the instant-restore snapshot retention (2 days), the daily retention (30 days)

az backup protection enable-for-vm --resource-group $Rg --vault-name rsv-az104-0502 `
  --vm vm-az104-0502 --policy-name DefaultPolicy
```

Now **start the first backup** (portal: vault > **Backup items** > **Azure Virtual Machine** > `vm-az104-0502` >
**Backup now**, keeping the default retention). It can take a while; carry on with Part 5 meanwhile.

**Create (but don't assign) an Enhanced policy** to see what it adds: vault > **Backup policies** > **Add** >
**Azure Virtual Machine** > **Enhanced**. Set **Hourly** every 4 hours and note the instant-restore range (up to 30
days). **Create** it, and leave it unassigned. Switching a VM from Enhanced back to Standard isn't possible.

## Part 3 - Restore

When the backup job shows **Completed** (`az backup job list -g $Rg -v rsv-az104-0502 -o table`):

1. **File recovery (walkthrough):** **Backup items** > the VM > **File Recovery**. Select a recovery point and read
   how it works: a script mounts the recovery point as drives on a machine you choose, you copy files back, then you
   unmount. Don't run the script.
2. **Restore disks:** **Restore VM** > the newest recovery point > **Create new** > **Restore disks**. Target resource
   group: create `rg-az104-lab-05-02-restore`. **Staging location**: create a small storage account when prompted.
   Then **Restore**.
3. When the restore job completes, open `rg-az104-lab-05-02-restore`. It holds the restored **managed disks**, and the
   job's details link to a generated **template** that would build a VM from them. **Don't deploy it**: reading it is
   the point.

## Part 4 - Backup alerts and reports

**Alerts.** Built-in job-failure alerts are on by default. To be notified, route them with an **alert processing
rule** and an **action group**. There's no alert rule to create, because these alerts come from Azure Backup itself:

```powershell
az monitor action-group create --resource-group $Rg --name ag-backup-0502 --short-name bkp0502 --action email me $Email
$agId = az monitor action-group show -g $Rg -n ag-backup-0502 --query id -o tsv
$rsvId = az backup vault show -g $Rg -n rsv-az104-0502 --query id -o tsv
az monitor alert-processing-rule create --resource-group $Rg --name route-backup-alerts-0502 `
  --scopes $rsvId --rule-type AddActionGroups --action-groups $agId --description "Backup alerts to email"
```

Teardown's first step disables soft delete, which fires a **Sev 0 security alert**, so this rule will email you then.

**Reports.** Send the vault's backup events to a workspace, in **resource-specific** mode:

1. Create a workspace: `az monitor log-analytics workspace create -g $Rg -n law-az104-0502 -l $Loc`.
2. Vault > **Diagnostic settings** > **Add**. Select the **Core Azure Backup** and **Addon Azure Backup** event
   categories, destination `law-az104-0502`, **resource specific**. Save.
3. Later, open **Resiliency** > **Monitoring + Reporting** > **Reports**, choose the workspace, and browse **Backup
   Items** and **Jobs**. Reports fill in once data arrives, which can take some hours. If it's still empty at teardown,
   that's expected; the query below shows the same data once it lands:

```kusto
AddonAzureBackupJobs
| summarize Jobs = count() by JobOperation, JobStatus
```

## Part 5 - Site Recovery: replicate, then test failover

Start this early: initial replication takes time.

1. VM > **Disaster recovery**. **Target region**: `$DrLoc`. On **Advanced settings**, note what Site Recovery will
   create: a target resource group, a target VNet, **replica managed disks**, and a **cache storage account** in the
   **source** region. Keep the replication policy defaults: 1-day recovery point retention, app-consistent snapshots
   off. **Review + Start replication**.
2. Watch the vault > **Replicated items** until the VM shows **Protected**. The Mobility service extension is now on
   the VM, and crash-consistent recovery points arrive every 5 minutes.
3. **Create an isolated VNet** in `$DrLoc` for the drill:
   `az network vnet create -g $Rg -n vnet-dr-test-0502 -l $DrLoc --address-prefix 10.52.0.0/16 --subnet-name test --subnet-prefixes 10.52.1.0/24`
4. **Replicated items** > the VM > **Test failover**. Choose the **latest processed** recovery point and the network
   `vnet-dr-test-0502`. Watch the job: a VM named `vm-az104-0502-test` comes up in `$DrLoc`. Replication to the real
   replicas continues unaffected.
5. Look at the test VM, then **Cleanup test failover** on the replicated item, with a note such as "Drill OK". The test
   VM and its resources are removed.

**Optional, with more cost: a real failover.** **Failover** > choose a recovery point > the VM stops in `$Loc` and runs in
`$DrLoc` > **Commit**. Note the VM is now **unprotected**: **Re-protect** would replicate it back, and **failback** is a
failover in the other direction. If you do this, the teardown below still applies, but delete resources in both
regions.

## Validation

```powershell
az backup item list -g $Rg -v rsv-az104-0502 --query "[].{item:properties.friendlyName, status:properties.protectionStatus}" -o table
az backup job list  -g $Rg -v rsv-az104-0502 --query "[].{op:properties.operation, status:properties.status}" -o table
az monitor alert-processing-rule list -g $Rg -o table
```

In the portal: **Replicated items** shows the VM **Protected**, and the last test failover **Succeeded**.

## Teardown

Do these **in order**.

### 1. Resources: Site Recovery first

1. If a test failover is still active, **Cleanup test failover**.
2. Vault > **Replicated items** > the VM > **Disable Replication**, removing the replication.
3. List what Site Recovery created in the target region (its resource group name ends in `-asr` by default) and the
   cache storage account in `$Rg`, and delete the target resource group:

```powershell
az group list --query "[?ends_with(name,'-asr') || contains(name,'0502')].{name:name, location:location}" -o table
# az group delete --name <the-target-resource-group-ending-in-asr> --yes
```

### 2. Resources: Backup, soft delete off FIRST

```powershell
# 1. Disable soft delete BEFORE deleting backup data. (This fires a Sev 0 security alert; Part 4 emails it to you.)
az backup vault backup-properties set -g $Rg -n rsv-az104-0502 --soft-delete-feature-state Disable

# 2. Stop protection AND delete the backup data
az backup protection disable -g $Rg -v rsv-az104-0502 --container-name vm-az104-0502 --item-name vm-az104-0502 `
  --backup-management-type AzureIaaSVM --delete-backup-data true --yes

# 3. Now the vault, and everything else in the lab resource groups, can go
az group delete --name rg-az104-lab-05-02-restore --yes
az group delete --name $Rg --yes
```

If you see the backup item in a **soft-deleted** state, soft delete was still on when the data was deleted. Undelete it,
disable soft delete, and delete it again; otherwise the vault waits 14 days.

### 3. Subscription scope

Azure Backup keeps **instant-restore snapshots** in a resource group it creates when you don't name one (by default a
name starting `AzureBackupRG_`). Check for it and delete it if this lab created it:

```powershell
az group list --query "[?starts_with(name,'AzureBackupRG')].{name:name, location:location}" -o table
```

### 4. Soft-deleted remains

None, if step 2 ran in order. The Log Analytics workspace can remain soft-deleted for up to 14 days (00-02).

### 5. Access

Remove any role you added to your working account only for this lab.

### 6. Verify

```powershell
az group exists --name $Rg                                                                # false
az backup vault list --query "[?contains(name,'0502')].name" -o tsv                      # nothing
az group list --query "[?ends_with(name,'-asr') || starts_with(name,'AzureBackupRG') || contains(name,'0502')].name" -o tsv   # nothing from this lab
```

Then mark teardown as confirmed in the Academy.
