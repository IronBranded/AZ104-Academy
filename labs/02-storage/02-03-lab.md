# Lab 02-03 - Azure Files and Blob Storage

**Objective:** Configure Azure Files and Azure Blob Storage
**Estimated cost:** Low - one Standard general-purpose v2 account (LRS) holding a few kilobytes,
including an HDD pay-as-you-go file share, deleted the same day. Part 3 archives one tiny blob.
Deleting it at teardown incurs a prorated early-deletion charge on those few kilobytes, which is
negligible but real.
**Licensing required:** None beyond an Azure subscription.

> Complete **02-02** first. The account stays **LRS** on purpose: archive isn't supported on ZRS,
> GZRS or RA-GZRS accounts.

Portal steps were checked against Microsoft Learn on 2026-09-30.

## Prerequisites

- **Owner** on the lab subscription.
- Azure PowerShell with `Az.Storage` and `Az.Resources`, and the Azure CLI for Part 3.

```powershell
$LabId = '02-03'
$Rg    = "rg-az104-lab-$LabId"
$Loc   = '<region>'
$Sa    = 'az104lab0203' + (Get-Random -Maximum 99999)
Connect-AzAccount
$Me    = (Get-AzContext).Account.Id

New-AzResourceGroup -Name $Rg -Location $Loc -Tag @{ 'az104-module' = $LabId } | Out-Null
$acct = New-AzStorageAccount -ResourceGroupName $Rg -Name $Sa -Location $Loc `
    -SkuName Standard_LRS -Kind StorageV2 -Tag @{ 'az104-module' = $LabId }
New-AzRoleAssignment -SignInName $Me -RoleDefinitionName 'Storage Blob Data Contributor' -Scope $acct.Id | Out-Null
# Allow up to 10 minutes for the data role, then:
$ctx = New-AzStorageContext -StorageAccountName $Sa -UseConnectedAccount
```

## Part 1 - Containers

```powershell
New-AzStorageContainer -Name 'Reports_2026' -Context $ctx    # fails: uppercase and underscore aren't allowed
New-AzStorageContainer -Name 'reports-2026' -Context $ctx | Out-Null

(Get-AzStorageAccount -ResourceGroupName $Rg -Name $Sa).AllowBlobPublicAccess
```

In the portal, open `reports-2026` > **Change access level**. Note the three levels: **Private**,
**Blob** and **Container**. If the account disallows anonymous access, the non-private levels can't
take effect. Leave it **Private**.

## Part 2 - Soft delete and versioning: which feature saves you

Turn on all three blob protections:

```powershell
Enable-AzStorageBlobDeleteRetentionPolicy      -ResourceGroupName $Rg -StorageAccountName $Sa -RetentionDays 7
Enable-AzStorageContainerDeleteRetentionPolicy -ResourceGroupName $Rg -StorageAccountName $Sa -RetentionDays 7
Update-AzStorageBlobServiceProperty -ResourceGroupName $Rg -StorageAccountName $Sa -IsVersioningEnabled $true | Out-Null
```

Write three versions of one blob, then delete it:

```powershell
foreach ($v in 'v1','v2','v3') {
    $v | Set-Content "$env:TEMP\plan.txt"
    Set-AzStorageBlobContent -File "$env:TEMP\plan.txt" -Container 'reports-2026' -Blob 'plan.txt' -Context $ctx -Force | Out-Null
}
Get-AzStorageBlob -Container 'reports-2026' -Prefix 'plan.txt' -Context $ctx -IncludeVersion |
    Select-Object Name, VersionId, IsLatestVersion

Remove-AzStorageBlob -Container 'reports-2026' -Blob 'plan.txt' -Context $ctx
Get-AzStorageBlob -Container 'reports-2026' -Prefix 'plan.txt' -Context $ctx -IncludeVersion |
    Select-Object Name, VersionId, IsLatestVersion      # no version is latest any more
```

Now restore it the way the lesson describes:

1. In the portal, open `plan.txt` in the container (show deleted blobs if needed) and select
   **Undelete**. The blob is **still not current**: with versioning on, Undelete doesn't restore the
   current version.
2. Open the **Versions** tab, select the `v2` version and choose **Make current version**. The
   PowerShell equivalent copies the version over the base blob:

```powershell
$v2 = Get-AzStorageBlob -Container 'reports-2026' -Prefix 'plan.txt' -Context $ctx -IncludeVersion |
    Sort-Object VersionId | Select-Object -Index 1
$v2 | Copy-AzStorageBlob -DestContainer 'reports-2026' -DestBlob 'plan.txt' -Force | Out-Null
```

Now delete a **whole container** and restore it. Container soft delete covers this case; blob soft delete doesn't:

```powershell
New-AzStorageContainer -Name 'scratch' -Context $ctx | Out-Null
Remove-AzStorageContainer -Name 'scratch' -Context $ctx -Force
```

In the portal: **Containers** > **Show deleted containers** > `scratch` > **Undelete**. It must come
back under its original name.

## Part 3 - Tiers and archive

```powershell
'archive me' | Set-Content "$env:TEMP\old.txt"
Set-AzStorageBlobContent -File "$env:TEMP\old.txt" -Container 'reports-2026' -Blob 'old.txt' `
    -StandardBlobTier Cool -Context $ctx | Out-Null
```

```bash
az storage blob set-tier --account-name "<account>" --container-name reports-2026 --name old.txt \
  --tier Archive --auth-mode login
```

In the portal, try to **Download** `old.txt`. It fails: an archived blob is offline. Its properties
and metadata are still visible. Then **Change tier** to **Hot**, with **Standard** rehydration
priority, and read the status on the blob: **rehydrate-pending-to-hot**. Standard can take up to
15 hours, so **don't wait for it**. Teardown deletes the account either way.

Also open **Configuration** and note the **default access tier**: hot, cool or cold, but never archive.

## Part 4 - A lifecycle management policy

**Data management** > **Lifecycle management** > **Add a rule**:

1. **Name:** `age-out-logs`. **Limit blobs with filters.** **Block blobs.** Tick **Base blobs** and
   **Previous versions**.
2. **Base blobs:** if last modified more than **30** days ago, **Move to cool storage**. Add
   conditions to move to archive at **90** days and **delete** at **365** days.
3. **Previous versions:** **delete** when created more than **90** days ago. This keeps
   versioning's storage growth in check.
4. **Filter set:** prefix `reports-2026/logs/`.

Open **Code view** and compare the JSON with the lesson's example. Then check the archive action:
does your rule include a `daysAfterLastTierChangeGreaterThan` condition? If not, a blob you
rehydrate could be archived again by this rule. Add one.

Nothing moves during the lab: the policy runs once a day, and your blobs are minutes old.

## Part 5 - Azure Files: snapshots versus share soft delete

```powershell
Get-AzStorageFileServiceProperty -ResourceGroupName $Rg -StorageAccountName $Sa |
    Select-Object -ExpandProperty ShareDeleteRetentionPolicy       # enabled by default on new accounts

New-AzRmStorageShare -ResourceGroupName $Rg -StorageAccountName $Sa -Name 'team' `
    -AccessTier TransactionOptimized -QuotaGiB 10 | Out-Null

# Is SMB's port reachable from where you are? This decides whether you could mount the share.
Test-NetConnection -ComputerName "$Sa.file.core.windows.net" -Port 445
```

In the portal, open the `team` share:

1. **Upload** a small text file, `notes.txt`.
2. **Snapshots** > **Add snapshot**. The snapshot is read-only and covers the whole share.
3. Delete `notes.txt` from the share. Then open the snapshot, find `notes.txt`, and **Restore** it.
   A **snapshot** restores a single file.
4. Now delete the **whole share**. Then **File shares** > **Show deleted shares** > `team` >
   **Undelete**. **Share soft delete** restores the share, with its snapshot.

Share soft delete couldn't have restored `notes.txt` on its own, and the snapshot alone couldn't have
survived deleting the share. Each feature covers one mistake.

## Validation

```powershell
$p = Get-AzStorageBlobServiceProperty -ResourceGroupName $Rg -StorageAccountName $Sa
$p.DeleteRetentionPolicy.Enabled, $p.ContainerDeleteRetentionPolicy.Enabled, $p.IsVersioningEnabled   # True True True
Get-AzStorageBlob -Container 'reports-2026' -Blob 'plan.txt' -Context $ctx | Select-Object Name, IsLatestVersion
(Get-AzStorageAccountManagementPolicy -ResourceGroupName $Rg -StorageAccountName $Sa).Policy.Rules.Name   # age-out-logs
Get-AzRmStorageShare -ResourceGroupName $Rg -StorageAccountName $Sa -Name 'team' | Select-Object Name, AccessTier, QuotaGiB
```

## Teardown

### 1. Resources

Remove the role assignment first, then delete the resource group.

```powershell
Remove-AzRoleAssignment -SignInName $Me -RoleDefinitionName 'Storage Blob Data Contributor' -Scope $acct.Id
Remove-AzResourceGroup -Name $Rg -Force
Remove-Item "$env:TEMP\plan.txt","$env:TEMP\old.txt" -ErrorAction SilentlyContinue
```

Deleting the **storage account** removes everything in it: soft-deleted blobs and containers,
versions, the soft-deleted share if any, and snapshots. None of those features protects the account
itself.

### 2. Subscription scope

```powershell
Get-AzRoleAssignment | Where-Object { -not $_.DisplayName } | Select-Object RoleDefinitionName, Scope
```

### 3. Directory scope

None.

### 4. Soft-deleted remains

None outside the deleted account. This is the point to remember: soft delete inside an account
doesn't survive deleting the account.

### 5. Access

Remove any role you added to your working account only for this lab.

### 6. Verify

```powershell
Get-AzResourceGroup -Name $Rg -ErrorAction SilentlyContinue                    # expect nothing
Get-AzStorageAccount | Where-Object StorageAccountName -like 'az104lab0203*'   # expect nothing
```

Then mark teardown as confirmed in the Academy.
