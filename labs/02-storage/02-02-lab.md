# Lab 02-02 - Storage Accounts

**Objective:** Configure and manage storage accounts
**Estimated cost:** Low - two Standard general-purpose v2 accounts holding a few kilobytes, with
blob versioning and change feed on, deleted the same day. Adding geo-redundancy incurs a data
transfer charge on those few kilobytes. Customer-managed keys are a walkthrough.
**Licensing required:** None beyond an Azure subscription.

> Complete **02-01** first. Both storage accounts bill for stored data and operations until
> teardown deletes the resource group.

Portal steps were checked against Microsoft Learn on 2026-09-30.

## Prerequisites

- **Owner** on the lab subscription.
- Azure PowerShell with `Az.Storage` and `Az.Resources`, in PowerShell 7 on Windows.
- **AzCopy v10**, downloaded from Microsoft's *Get started with AzCopy* page (see the lesson's
  Sources) and extracted to a folder on your `PATH`. Part 5 only.
- **Azure Storage Explorer**, optional, for Part 6.

```powershell
$LabId = '02-02'
$Rg    = "rg-az104-lab-$LabId"
$Loc   = '<region>'
$n     = Get-Random -Maximum 99999
$Src   = "az104lab0202s$n"
$Dst   = "az104lab0202d$n"
Connect-AzAccount
$Me    = (Get-AzContext).Account.Id
New-AzResourceGroup -Name $Rg -Location $Loc -Tag @{ 'az104-module' = $LabId } | Out-Null
```

## Part 1 - Create: the decisions you can't take back

```powershell
# Names: 3-24 characters, numbers and lowercase letters only. This fails:
New-AzStorageAccount -ResourceGroupName $Rg -Name "AZ104Lab$n" -Location $Loc -SkuName Standard_LRS -Kind StorageV2

# Source: plain general-purpose v2, LRS
$srcAcct = New-AzStorageAccount -ResourceGroupName $Rg -Name $Src -Location $Loc `
    -SkuName Standard_LRS -Kind StorageV2 -Tag @{ 'az104-module' = $LabId }

# Destination: infrastructure (double) encryption, which is only possible at creation
$dstAcct = New-AzStorageAccount -ResourceGroupName $Rg -Name $Dst -Location $Loc `
    -SkuName Standard_LRS -Kind StorageV2 -RequireInfrastructureEncryption -Tag @{ 'az104-module' = $LabId }
```

In the portal, open **Encryption** on each account. Both use **Microsoft-managed keys**. Only the
destination shows infrastructure encryption **enabled**, and the source offers no way to turn it on.

## Part 2 - Redundancy: when the secondary becomes readable

```powershell
$srcAcct.SecondaryEndpoints            # empty: LRS has no secondary

Set-AzStorageAccount -ResourceGroupName $Rg -Name $Src -SkuName Standard_GRS | Out-Null
(Get-AzStorageAccount -ResourceGroupName $Rg -Name $Src).SecondaryEndpoints.Blob    # still no readable endpoint

Set-AzStorageAccount -ResourceGroupName $Rg -Name $Src -SkuName Standard_RAGRS | Out-Null
(Get-AzStorageAccount -ResourceGroupName $Rg -Name $Src).SecondaryEndpoints.Blob    # a -secondary endpoint appears
```

Open the source account's **Redundancy** page. It shows the **secondary region**, which is the paired
region. You didn't choose it, and you can't. Look at the zone-redundant options it offers, but
**don't** start a zonal conversion: those usually start within about 72 hours, have no completion
SLA, and would outlive this lab.

## Part 3 - Encryption scopes (portal)

1. On the **source** account: **Encryption** > **Encryption scopes** > **Add**. Name it `scope-a`,
   with **Microsoft-managed keys**.
2. **Containers** > **+ Container** named `scoped`. Under **Advanced**, set the **default encryption
   scope** to `scope-a`. This can only be set now, while creating the container.
3. Back in **Encryption scopes**: note there's no **Delete**, only **Disable**. A scope can't be
   deleted; teardown removes it with the account.
4. **Customer-managed keys, walkthrough only:** on **Encryption**, select **Customer-managed keys**
   and read the requirements. A key vault with **soft delete and purge protection**, an RSA key, and
   a managed identity with **get, wrapkey and unwrapkey**. **Cancel.** Purge protection can't be
   turned off, so a lab key vault would sit undeletable for its whole retention period.

## Part 4 - Object replication

Give yourself a data role on both accounts, so you can use Entra authorization:

```powershell
New-AzRoleAssignment -SignInName $Me -RoleDefinitionName 'Storage Blob Data Contributor' `
    -ResourceGroupName $Rg | Out-Null
# Allow up to 10 minutes before the uploads below.
$sctx = New-AzStorageContext -StorageAccountName $Src -UseConnectedAccount
$dctx = New-AzStorageContext -StorageAccountName $Dst -UseConnectedAccount
```

Prerequisites, containers, and one blob that exists **before** the policy:

```powershell
Update-AzStorageBlobServiceProperty -ResourceGroupName $Rg -StorageAccountName $Src `
    -EnableChangeFeed $true -IsVersioningEnabled $true | Out-Null
Update-AzStorageBlobServiceProperty -ResourceGroupName $Rg -StorageAccountName $Dst `
    -IsVersioningEnabled $true | Out-Null

New-AzStorageContainer -Name 'reports' -Context $sctx | Out-Null
New-AzStorageContainer -Name 'reports-copy' -Context $dctx | Out-Null

'before the policy' | Set-Content "$env:TEMP\before.txt"
Set-AzStorageBlobContent -File "$env:TEMP\before.txt" -Container 'reports' -Blob 'before.txt' -Context $sctx | Out-Null
```

The policy: **destination first**, identified by the source's full resource ID. Cross-tenant
replication is disallowed by default on new accounts, which makes the ID mandatory.

```powershell
$rule = New-AzStorageObjectReplicationPolicyRule -SourceContainer 'reports' -DestinationContainer 'reports-copy'
$pol  = Set-AzStorageObjectReplicationPolicy -ResourceGroupName $Rg -StorageAccountName $Dst `
    -PolicyId default -SourceAccount $srcAcct.Id -Rule $rule
Set-AzStorageObjectReplicationPolicy -ResourceGroupName $Rg -StorageAccountName $Src -InputObject $pol | Out-Null

'after the policy' | Set-Content "$env:TEMP\after.txt"
Set-AzStorageBlobContent -File "$env:TEMP\after.txt" -Container 'reports' -Blob 'after.txt' -Context $sctx | Out-Null
```

Replication is asynchronous. Wait a few minutes, then:

```powershell
Get-AzStorageBlob -Container 'reports-copy' -Context $dctx | Select-Object Name
# after.txt only. before.txt existed before the rule, and rules copy new blobs by default.

Set-AzStorageBlobContent -File "$env:TEMP\after.txt" -Container 'reports-copy' -Blob 'mine.txt' -Context $dctx
# Fails with 409 Conflict: the destination container is read-only while the rule exists.
```

In the portal, open `after.txt` in the source container. Its properties show its object
replication status.

## Part 5 - AzCopy

Reuse this PowerShell session's sign-in, so there's no separate `azcopy login`:

```powershell
$Env:AZCOPY_AUTO_LOGIN_TYPE = 'PSCRED'
$Env:AZCOPY_TENANT_ID       = (Get-AzContext).Tenant.Id

# Server-to-server: the data goes account to account, not through your machine
azcopy make "https://$Dst.blob.core.windows.net/copied"
azcopy copy "https://$Src.blob.core.windows.net/reports" "https://$Dst.blob.core.windows.net/copied" --recursive

# One-way sync from a local folder
New-Item -ItemType Directory "$env:TEMP\az104-sync" -Force | Out-Null
'one' | Set-Content "$env:TEMP\az104-sync\one.txt"
azcopy make "https://$Src.blob.core.windows.net/synced"
azcopy sync "$env:TEMP\az104-sync" "https://$Src.blob.core.windows.net/synced" --recursive

'two' | Set-Content "$env:TEMP\az104-sync\two.txt"
azcopy sync "$env:TEMP\az104-sync" "https://$Src.blob.core.windows.net/synced" --recursive
# The summary shows only the new file transferred.
```

If AzCopy returns 403, the data role from Part 4 hasn't propagated yet, or the session lost its
token. Being Owner isn't enough.

## Validation

```powershell
(Get-AzStorageAccount -ResourceGroupName $Rg -Name $Src).Sku.Name               # Standard_RAGRS
(Get-AzStorageAccount -ResourceGroupName $Rg -Name $Dst).Encryption.RequireInfrastructureEncryption   # True
Get-AzStorageObjectReplicationPolicy -ResourceGroupName $Rg -StorageAccountName $Dst | Select-Object PolicyId, SourceAccount
Get-AzStorageBlob -Container 'copied' -Context $dctx | Select-Object Name
```

## Teardown

### 1. Resources

Remove your role assignment first. It's scoped to the resource group you're about to delete:

```powershell
Remove-AzRoleAssignment -SignInName $Me -RoleDefinitionName 'Storage Blob Data Contributor' -ResourceGroupName $Rg
Remove-AzResourceGroup -Name $Rg -Force
Remove-Item "$env:TEMP\before.txt","$env:TEMP\after.txt" -ErrorAction SilentlyContinue
Remove-Item "$env:TEMP\az104-sync" -Recurse -ErrorAction SilentlyContinue
Remove-Item Env:AZCOPY_AUTO_LOGIN_TYPE, Env:AZCOPY_TENANT_ID -ErrorAction SilentlyContinue
```

Deleting both accounts removes the object replication policy, the encryption scope, and every blob
version.

### 2. Subscription scope

```powershell
Get-AzRoleAssignment | Where-Object { -not $_.DisplayName } | Select-Object RoleDefinitionName, Scope
```

### 3. Directory scope

None.

### 4. Soft-deleted remains

None. Blob soft delete wasn't enabled; module 02-03 covers it.

### 5. Access

Remove any role you added to your working account only for this lab.

### 6. Verify

```powershell
Get-AzResourceGroup -Name $Rg -ErrorAction SilentlyContinue                       # expect nothing
Get-AzStorageAccount | Where-Object StorageAccountName -like 'az104lab0202*'      # expect nothing
```

Then mark teardown as confirmed in the Academy.
