# Lab 02-01 - Configuring Access to Storage

**Objective:** Configure access to storage
**Estimated cost:** Low - one Standard general-purpose v2 storage account (LRS) holding a
few kilobytes, plus an empty virtual network, which Azure doesn't charge for. Delete it the
same day. Part 6 is a walkthrough and creates nothing.
**Licensing required:** None beyond an Azure subscription.

> Complete **Module 0** and **01-02** first. This is the first lab that creates a billable
> resource: a storage account bills for the data it holds and the operations against it.
> Teardown deletes the whole resource group.

Portal steps were checked against Microsoft Learn on 2026-09-30.

## Why this matters

Data in a storage account is reached over the internet by default, and several kinds of credential can open it: account keys, shared access signatures and Microsoft Entra identities. An administrator has to decide which networks may reach the account, which credentials are allowed, and how to take access back when one leaks.

## The desired state

When you finish, these will be true. Each one is checked in **Validation** below.

- A storage account that accepts **Microsoft Entra** authorization and refuses **Shared Key** (account keys, and the SAS tokens signed with them).
- A **key expiration** reminder of 60 days.
- A **firewall** that denies by default and allows one subnet through a virtual network rule.
- First-hand experience of each SAS type, and of revoking each one.

## Prerequisites

- **Owner** on the lab subscription. You create a role assignment, rotate keys, and change
  network rules.
- Azure PowerShell with `Az.Storage`, `Az.Network` and `Az.Resources`. The commands are written
  for PowerShell 7 on Windows.

```powershell
$LabId = '02-01'
$Rg    = "rg-az104-lab-$LabId"
$Loc   = '<region>'
$Sa    = 'az104lab0201' + (Get-Random -Maximum 99999)   # globally unique, lowercase, 3-24 chars
Connect-AzAccount
$Me    = (Get-AzContext).Account.Id

function Test-Sas([string]$Uri) {
    try   { "OK $((Invoke-WebRequest -Uri $Uri -UseBasicParsing).StatusCode)" }
    catch { "FAILED $([int]$_.Exception.Response.StatusCode)" }
}
```

## Part 1 - A storage account, and why Owner can't read it

```powershell
New-AzResourceGroup -Name $Rg -Location $Loc -Tag @{ 'az104-module' = $LabId }
$acct = New-AzStorageAccount -ResourceGroupName $Rg -Name $Sa -Location $Loc `
    -SkuName Standard_LRS -Kind StorageV2 -AllowSharedKeyAccess $true -Tag @{ 'az104-module' = $LabId }
```

In the portal, open the account > **Containers**. As Owner, you can manage the account, but
reading data *with your Entra identity* needs a data role (01-02: Owner has no `DataActions`).
Give yourself one:

```powershell
New-AzRoleAssignment -SignInName $Me -RoleDefinitionName 'Storage Blob Data Contributor' -Scope $acct.Id
```

Wait up to 10 minutes for the role to take effect, then create a container and a blob using
**Entra authorization**, with no key involved:

```powershell
$ctx = New-AzStorageContext -StorageAccountName $Sa -UseConnectedAccount
New-AzStorageContainer -Name 'lab' -Context $ctx | Out-Null
'hello from 02-01' | Set-Content "$env:TEMP\hello.txt"
Set-AzStorageBlobContent -File "$env:TEMP\hello.txt" -Container 'lab' -Blob 'hello.txt' -Context $ctx | Out-Null
```

## Part 2 - Three kinds of SAS

```powershell
# A key-based context, signed with key1
$key1 = (Get-AzStorageAccountKey -ResourceGroupName $Rg -Name $Sa)[0].Value
$kctx = New-AzStorageContext -StorageAccountName $Sa -StorageAccountKey $key1

# (A) Ad hoc service SAS, signed with key1
$sasAdhoc = New-AzStorageBlobSASToken -Context $kctx -Container 'lab' -Blob 'hello.txt' `
    -Permission r -ExpiryTime (Get-Date).AddHours(2) -FullUri

# (B) Service SAS bound to a stored access policy on the container
New-AzStorageContainerStoredAccessPolicy -Container 'lab' -Policy 'readers-v1' `
    -Permission r -ExpiryTime (Get-Date).AddDays(1) -Context $kctx | Out-Null
$sasPolicy = New-AzStorageBlobSASToken -Context $kctx -Container 'lab' -Blob 'hello.txt' `
    -Policy 'readers-v1' -FullUri

# (C) User delegation SAS, signed with Entra credentials, not a key
$sasUds = New-AzStorageBlobSASToken -Context $ctx -Container 'lab' -Blob 'hello.txt' `
    -Permission r -ExpiryTime (Get-Date).AddHours(2) -FullUri

Test-Sas $sasAdhoc; Test-Sas $sasPolicy; Test-Sas $sasUds    # all OK 200
```

Look at each URI. **B** carries `si=readers-v1` instead of its own expiry and permissions.
**C** carries extra `sk…` fields describing the user delegation key.

## Part 3 - Revoke them one mechanism at a time

Predict each result before you run it.

```powershell
# 1. Delete the stored access policy: only B dies
Remove-AzStorageContainerStoredAccessPolicy -Container 'lab' -Policy 'readers-v1' -Context $kctx
Test-Sas $sasAdhoc; Test-Sas $sasPolicy; Test-Sas $sasUds

# 2. Regenerate key1: A dies (it was signed with key1). C survives: it has no key.
New-AzStorageAccountKey -ResourceGroupName $Rg -Name $Sa -KeyName key1 | Out-Null
Test-Sas $sasAdhoc; Test-Sas $sasUds

# 3. Revoke the user delegation keys: C dies. Allow a few minutes; the keys are cached.
Revoke-AzStorageAccountUserDelegationKeys -ResourceGroupName $Rg -StorageAccountName $Sa
Test-Sas $sasUds
```

If you had re-created `readers-v1` with the same name in step 1, token B would have come back to
life. That's why a revoked policy gets a **new** name.

## Part 4 - Key hygiene: a rotation reminder, then no keys at all

```powershell
# A rotation REMINDER at 60 days. It doesn't rotate anything.
Set-AzStorageAccount -ResourceGroupName $Rg -Name $Sa -KeyExpirationPeriodInDay 60 | Out-Null
(Get-AzStorageAccount -ResourceGroupName $Rg -Name $Sa).KeyPolicy

# Make a fresh key-signed SAS and a fresh user delegation SAS, then disallow Shared Key
$key1   = (Get-AzStorageAccountKey -ResourceGroupName $Rg -Name $Sa)[0].Value
$kctx   = New-AzStorageContext -StorageAccountName $Sa -StorageAccountKey $key1
$sasKey = New-AzStorageBlobSASToken -Context $kctx -Container 'lab' -Blob 'hello.txt' -Permission r -ExpiryTime (Get-Date).AddHours(1) -FullUri
$sasUd2 = New-AzStorageBlobSASToken -Context $ctx  -Container 'lab' -Blob 'hello.txt' -Permission r -ExpiryTime (Get-Date).AddHours(1) -FullUri

Set-AzStorageAccount -ResourceGroupName $Rg -Name $Sa -AllowSharedKeyAccess $false | Out-Null
Test-Sas $sasKey    # FAILED 403: a service SAS is Shared Key authorization
Test-Sas $sasUd2    # OK 200: Entra-signed
```

In the portal, **Access keys** still shows two keys, but nothing signed with them works any more.

## Part 5 - The firewall: a valid token, refused

1. **Networking** > **Public network access**: **Enabled from selected virtual networks and IP
   addresses**. Under **Firewall**, tick **Add your client IP address** and **Save**.
2. Run `Test-Sas $sasUd2`. **OK**: you're inside the boundary, and the token is valid.
3. Try adding `10.0.0.1` as an IP address. It's **rejected**: private ranges aren't allowed in IP
   rules.
4. Now remove your own IP:

```powershell
(Get-AzStorageAccountNetworkRuleSet -ResourceGroupName $Rg -Name $Sa).IpRules |
    ForEach-Object { Remove-AzStorageAccountNetworkRule -ResourceGroupName $Rg -Name $Sa -IPAddressOrRange $_.IPAddressOrRange | Out-Null }
Test-Sas $sasUd2    # FAILED 403: the token is still valid; the network gate refuses it
```

If the first request after the change still succeeds, retry after a short wait. Then open
**Containers** in the portal: browsing blobs fails, because it's data plane. **Networking** still
opens and saves normally, because settings are control plane.

5. Add a **virtual network rule**. Create an empty virtual network (free):

```powershell
$sub  = New-AzVirtualNetworkSubnetConfig -Name 'apps' -AddressPrefix '10.21.1.0/24'
New-AzVirtualNetwork -Name 'vnet-az104-02-01' -ResourceGroupName $Rg -Location $Loc `
    -AddressPrefix '10.21.0.0/16' -Subnet $sub | Out-Null
```

   In **Networking** > **Virtual networks** > **Add existing virtual network**, choose the `apps`
   subnet and save. Then open the virtual network > **Subnets** > `apps`. A **Microsoft.Storage**
   service endpoint now appears; the portal created it for you. From PowerShell or the CLI, you
   would add the endpoint yourself first.

## Part 6 - Azure Files identity-based access (walkthrough)

Identity-based access needs a directory service: AD DS with synced users, Microsoft Entra Domain
Services, or Microsoft Entra Kerberos with joined clients. Most lab tenants don't have one, so this
part is read-only.

1. Open the storage account > **Data storage** > the file shares page. Under
   **Identity-based access**, select **Not configured** and read the three identity sources
   offered. Name the one that needs **no** domain controller line of sight for clients.
2. Note that the page lets you enable only **one** source for the whole account.
3. **Access control (IAM)** > **Add role assignment**, then search for `Storage File Data SMB`.
   Read the descriptions of **Share Reader**, **Share Contributor** and **Share Elevated
   Contributor**. **Cancel** without assigning anything.
4. From the lesson: after a source is enabled, the **default share-level permission** is
   **None**. And even with a share role, **Windows ACLs** still decide access to the root
   directory and everything below it.

## What just happened?

Every request passed two separate gates. The **network gate** (the firewall) decided whether the request could reach the account at all, which is why a perfectly valid token was refused from the wrong network. The **authorization gate** decided what the caller could do. Owner of the account still couldn't read blobs without a **data** role, because managing the account and reading its data are different permissions. Each SAS type was revoked by a different mechanism, which is the distinction the exam tests.

This deletes the storage account, its data, and the virtual network.

Your **Storage Blob Data Contributor** assignment was scoped to the storage account. Confirm
nothing orphaned remains. List without `-Scope`, so assignments at every scope are included:

```powershell
Get-AzRoleAssignment | Where-Object { -not $_.DisplayName -or $_.Scope -like "*$Sa*" } |
    Select-Object RoleDefinitionName, Scope
```

Remove anything it returns for this lab with `Remove-AzRoleAssignment`.
