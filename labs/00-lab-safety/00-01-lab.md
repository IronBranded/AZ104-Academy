# Lab 00-01 - Cost Guardrails and Budget Alerts

**Objective:** (Project prerequisite - not an AZ-104 exam objective)
**Estimated cost:** $0 — budgets and action groups are free; the Automation
account free tier covers the runbook minutes.
**Licensing required:** None beyond an Azure subscription.

> This is the one lab in the guide with no prerequisite lab, because everything
> else depends on it. Run it before you create anything billable.
> Use the narrowest role that lets you finish, and remove anything you added only
> for this lab in teardown.

## Why this matters

A self-funded lab subscription has nobody watching the bill except you. Azure keeps charging for what exists, whether or not you are looking at it, and cost data arrives hours late. Before you create anything billable, you need an alarm that tells you, and a brake that acts on its own.

## The desired state

When you finish, these will be true. Each one is checked in **Validation** below.

- A **budget** on the subscription, with notifications that call an **action group**.
- An **Automation runbook** that can stop lab compute, running under a **managed identity** that holds just enough access.
- A **webhook** that lets the action group start the runbook.
- A bookmarked **Cost analysis** view grouped by service, to check at the end of every session.

## Prerequisites

- An Azure subscription where you hold **Owner** or **Contributor + User Access
  Administrator** at subscription scope.
- `Az.Accounts`, `Az.Billing`, `Az.Monitor`, `Az.Security`, `Az.Automation`,
  `Az.Resources`.
- A real monthly ceiling in mind. Pick the number that would actually hurt.

```powershell
Install-Module Az -Scope CurrentUser -Repository PSGallery

```

## Part 1 - Budget, action group and spending brake

### Method A - Portal

#### A1. Create the long-lived resource group

1. **Azure portal** → **Resource groups** → **Create**.
2. Subscription: your lab subscription. Name: `rg-az104-core`. Region: pick one
   near you and use it consistently.
3. **Review + create** → **Create**.

This resource group is **not** torn down between labs.

#### A2. Create the action group

1. **Monitor** → **Alerts** → **Action groups** → **Create**.
2. Resource group `rg-az104-core`. Action group name `ag-az104-budget-brake`.
   Display name `AZ104Brake` (12 characters maximum — this is the short name
   that appears in SMS and email subject lines).
3. **Notifications** tab → Notification type **Email/SMS message/Push/Voice** →
   name it `me` → tick **Email** and enter your address → **OK**.
4. **Actions** tab: leave empty for now. You will add the runbook in A4 once it
   exists.
5. **Review + create** → **Create**.

#### A3. Create the budget

1. **Cost Management + Billing** → select your billing scope → **Cost
   Management** → **Budgets** → **Add**.
2. Scope: **Subscription**. Name `bud-az104-monthly`.
3. Reset period **Monthly**. Creation date: the first of the current month.
   Expiration date: a year out.
4. Amount: your ceiling. **Next**.
5. Configure three alert conditions:

   | Type | % of budget | Action group |
   | --- | --- | --- |
   | Forecasted | 80 | — |
   | Actual | 90 | — |
   | Actual | 100 | `ag-az104-budget-brake` |

6. Alert recipients: your email address.
7. **Create**.

Note what the form let you do: nothing here stops spending. Everything on this
page is a notification.

#### A4. Create the Automation account and brake runbook

1. **Automation Accounts** → **Create**. Resource group `rg-az104-core`, name
   `aa-az104-brake`. On the **Advanced** tab, enable the
   **System assigned** managed identity. **Review + create**.
2. Once deployed: **Identity** → **System assigned** → **Azure role
   assignments** → **Add role assignment**. Scope **Subscription**, role
   **Contributor**. Save.

   > Contributor is enough to deallocate VMs and scale sets.
   > Do not grant Owner. The brake should not be able to hand out access.

3. **Runbooks** → **Create a runbook**. Name `Stop-LabCompute`, type
   **PowerShell**, runtime version **7.2** or later. **Create**.
4. Paste the contents of
   [`scripts/00-lab-safety/Stop-LabCompute.ps1`](../../scripts/00-lab-safety/Stop-LabCompute.ps1).
5. **Save** → **Publish**.
6. **Webhooks** → **Add webhook** → **Create new webhook**. Name
   `wh-az104-brake`, expiry a year out. **Copy the URL now** — it is shown once
   and never again. Leave parameters empty. **Create**.
7. Back in **Monitor** → **Action groups** → `ag-az104-budget-brake` →
   **Actions** → type **Webhook**, name `brake`, paste the URL. Leave "Enable
   the common alert schema" **off** (the runbook does not parse the payload).
   **Save changes**.

#### A5. Verify

1. **Cost Management** → **Budgets** → confirm three alert conditions and that
   the 100% condition lists the action group.
2. **Monitor** → **Action groups** → `ag-az104-budget-brake` → **Test action
   group**. Pick any sample alert type, run the test, and confirm you get the
   email and that the runbook shows a completed job under **Automation
   Accounts** → **Jobs**.

Testing the action group is the step most people skip. An untested brake is a
brake you are assuming works.

### Method B - PowerShell

**Modules:** `Az.Resources`, `Az.Monitor`, `Az.Billing`, `Az.Automation`, `Az.Security`

```powershell
#region Parameters
$Location       = 'canadacentral'
$CoreRg         = 'rg-az104-core'
$ActionGroup    = 'ag-az104-budget-brake'
$ShortName      = 'AZ104Brake'          # max 12 chars
$BudgetName     = 'bud-az104-monthly'
$BudgetAmount   = 150                    # your real ceiling
$AlertEmail     = 'you@example.com'
$AutomationName = 'aa-az104-brake'
$SubId          = (Get-AzContext).Subscription.Id
#endregion

# 1. Long-lived resource group
New-AzResourceGroup -Name $CoreRg -Location $Location -Tag @{ 'az104-module' = '00-01' } -Force

# 2. Action group with an email receiver
$emailReceiver = New-AzActionGroupReceiver -Name 'me' -EmailAddress $AlertEmail
$ag = Set-AzActionGroup -ResourceGroupName $CoreRg `
                        -Name $ActionGroup `
                        -ShortName $ShortName `
                        -Receiver $emailReceiver
$ActionGroupId = $ag.Id
$ActionGroupId

# 3. Budget with three notifications.
#    NOTE: -NotificationThreshold is a WHOLE-NUMBER PERCENTAGE. 80 means 80%.
#    Passing 0.8 means 0.8% and will fire on the first cent of spend.
$startDate = (Get-Date -Day 1).Date        # monthly budgets must start on the 1st

New-AzConsumptionBudget -Name $BudgetName `
                        -Amount $BudgetAmount `
                        -Category Cost `
                        -TimeGrain Monthly `
                        -StartDate $startDate `
                        -EndDate $startDate.AddYears(1) `
                        -NotificationKey 'warn-actual-90' `
                        -NotificationEnabled `
                        -NotificationThreshold 90 `
                        -ContactEmail $AlertEmail

# Add the braking notification that calls the action group
Set-AzConsumptionBudget -Name $BudgetName `
                        -Amount $BudgetAmount `
                        -Category Cost `
                        -TimeGrain Monthly `
                        -StartDate $startDate `
                        -EndDate $startDate.AddYears(1) `
                        -NotificationKey 'brake-actual-100' `
                        -NotificationEnabled `
                        -NotificationThreshold 100 `
                        -ContactEmail $AlertEmail `
                        -ContactGroup $ActionGroupId

Get-AzConsumptionBudget -Name $BudgetName | Format-List Name, Amount, TimeGrain, Notification
```

> **Forecasted notifications.** `New-AzConsumptionBudget` exposes threshold and
> contact settings but not the `thresholdType` field, so it creates `Actual`
> notifications only. To add the forecasted-at-80 alert, use the portal (A3) or
> PUT the budget directly against the
> `Microsoft.Consumption/budgets` REST API with
> `"thresholdType": "Forecasted"`. This is a real gap in the cmdlet, not a
> mistake on your side — worth knowing before you spend an hour on it.

```powershell
# 4. Automation account with a system-assigned managed identity
$aa = New-AzAutomationAccount -ResourceGroupName $CoreRg `
                              -Name $AutomationName `
                              -Location $Location `
                              -AssignSystemIdentity

# 5. Contributor at subscription scope for the managed identity
New-AzRoleAssignment -ObjectId $aa.Identity.PrincipalId `
                     -RoleDefinitionName 'Contributor' `
                     -Scope "/subscriptions/$SubId"

# 6. Import and publish the runbook
Import-AzAutomationRunbook -ResourceGroupName $CoreRg `
                           -AutomationAccountName $AutomationName `
                           -Name 'Stop-LabCompute' `
                           -Type PowerShell `
                           -Path '.\scripts\00-lab-safety\Stop-LabCompute.ps1' `
                           -Published -Force

# 7. Webhook. The URI is returned ONCE. Capture it before the variable goes away.
$wh = New-AzAutomationWebhook -ResourceGroupName $CoreRg `
                              -AutomationAccountName $AutomationName `
                              -RunbookName 'Stop-LabCompute' `
                              -Name 'wh-az104-brake' `
                              -IsEnabled $true `
                              -ExpiryTime (Get-Date).AddYears(1) `
                              -Force
$wh.WebhookURI     # copy this now

# 8. Add the webhook to the action group alongside the email receiver
$webhookReceiver = New-AzActionGroupReceiver -Name 'brake' `
                                             -WebhookReceiver `
                                             -ServiceUri $wh.WebhookURI
Set-AzActionGroup -ResourceGroupName $CoreRg `
                  -Name $ActionGroup `
                  -ShortName $ShortName `
                  -Receiver $emailReceiver, $webhookReceiver
```

## Validation

Prove each link in the chain independently. A chain you have only tested
end-to-end fails in a way you cannot diagnose.

```powershell
# The budget exists and knows about the action group
(Get-AzConsumptionBudget -Name $BudgetName).Notification.Values |
    Select-Object Enabled, Operator, Threshold, ContactGroups

# The runbook is published
Get-AzAutomationRunbook -ResourceGroupName $CoreRg -AutomationAccountName $AutomationName |
    Select-Object Name, State, RunbookType

# The managed identity actually holds Contributor
Get-AzRoleAssignment -ObjectId $aa.Identity.PrincipalId | Select-Object RoleDefinitionName, Scope

# Fire the runbook by hand in WhatIf mode and read the output
$job = Start-AzAutomationRunbook -ResourceGroupName $CoreRg `
                                 -AutomationAccountName $AutomationName `
                                 -Name 'Stop-LabCompute' `
                                 -Parameters @{ WhatIfMode = $true }
Start-Sleep 45
Get-AzAutomationJobOutput -ResourceGroupName $CoreRg `
                          -AutomationAccountName $AutomationName `
                          -Id $job.JobId -Stream Any |
    Get-AzAutomationJobOutputRecord | Select-Object -ExpandProperty Value
```

Then fire the webhook end to end:

```powershell
Invoke-RestMethod -Method Post -Uri $wh.WebhookURI -Body '{}' -ContentType 'application/json'
```

Confirm a new job appears. If it does not, the webhook is the broken link, not
the runbook.

### Portal validation

Cost Management → **Cost analysis** → group by **Service name**, daily
granularity. Bookmark it. This is the view you check at the end of every study
session; a new service appearing in it that you did not expect is the signal.

### Validation checklist

Tick each check only after you have seen the expected result yourself. The lab counts as **validated** when every box here is ticked.

- [ ] The budget's notifications list your action group under `ContactGroups`.
- [ ] The `Stop-LabCompute` runbook shows the state **Published**.
- [ ] The Automation account's managed identity holds **Contributor** at the scope you chose.
- [ ] The WhatIf job output lists what it *would* stop, and stops nothing.
- [ ] Posting to the webhook creates a new runbook job.

## What just happened?

You built a chain with three independent links: the **budget** notices spend, the **action group** carries the message, and the **runbook** acts. You tested each link on its own because a chain tested only end to end fails in a way you can't diagnose. Notice what the managed identity did: the runbook signs in as an Azure identity with a role assignment, the same principal-role-scope model module 01-02 teaches. And notice the limit: cost data lags by hours, so the budget is an alarm, not a circuit breaker.

## Teardown

**This lab is the exception: do not tear it down.** `rg-az104-core`, the budget,
the action group, and the Automation account persist for the whole guide.

Only if you are abandoning the lab tenant entirely:

### 1. Resources
- [ ] `Remove-AzResourceGroup -Name rg-az104-core -Force`

### 2. Subscription scope
- [ ] `Remove-AzConsumptionBudget -Name bud-az104-monthly`
- [ ] Remove the Contributor assignment held by the Automation account's managed
      identity — deleting the account leaves the role assignment orphaned:
      `Get-AzRoleAssignment | Where-Object { -not $_.DisplayName }`

### 3. Directory scope
- [ ] None created by this lab.

### 4. Soft-deleted remains
- [ ] Automation accounts have no soft delete. Nothing to purge.

### 5. Access
- [ ] Remove any Azure or Microsoft Entra role you assigned to your working
      account only for this lab.

### 6. Verify
- [ ] `Get-AzConsumptionBudget` returns nothing
- [ ] `Get-AzActionGroup -ResourceGroupName rg-az104-core` errors with
      "resource group not found"
