**Objective:** Manage access to Azure resources
**Estimated cost:** Free - an empty resource group, a test user, two groups and role

**Licensing required:** None beyond an Azure subscription. Azure RBAC is included.

> Complete **Module 0B** and **01-01** first. Run this in your **lab subscription**.
> Part 3 creates an assignment at **subscription** scope: it reaches every resource
> group, including `rg-az104-core`, until teardown removes it.

Portal steps were checked against Microsoft Learn on 2026-09-30. If a label differs,
the Microsoft Learn page in the lesson's Sources is the reference.

## Why this matters

A user who exists in the directory still can't touch a single Azure resource. Every action on a resource needs an Azure role assignment, and in a real subscription access arrives by several paths at once: directly, through groups, inherited from higher scopes. An administrator has to grant it at the narrowest scope that works, and read it back correctly.

## The desired state

When you finish, these will be true. Each one is checked in **Validation** below.

- A user, **Dana**, who receives **Reader** at subscription scope through a **nested group**.
- A direct **Contributor** assignment on the lab resource group, created and then removed.
- The ability to explain, from the assignment list alone, exactly what Dana can do and why.

## Prerequisites

- On the lab subscription: **Owner**, or **Contributor** plus **User Access
  Administrator** or **Role Based Access Control Administrator**. You need to create a
  resource group *and* role assignments.
- In Microsoft Entra ID: **User Administrator**, to create the test user and groups.
- Azure PowerShell (`Az.Resources`) and Microsoft Graph PowerShell, or the Azure CLI.

```powershell
$LabId  = '01-02'
$Prefix = "az104-$LabId"
$Domain = '<tenant>.onmicrosoft.com'
$Rg     = "rg-az104-lab-$LabId"
Connect-AzAccount
Connect-MgGraph -Scopes 'User.ReadWrite.All', 'Group.ReadWrite.All'
$SubId  = (Get-AzContext).Subscription.Id
```

## Part 1 - Set up the principals and the scope

```powershell
New-AzResourceGroup -Name $Rg -Location '<region>' -Tag @{ 'az104-module' = $LabId }

$pw   = @{ Password = '<temporary-password>'; ForceChangePasswordNextSignIn = $true }
$dana = New-MgUser -DisplayName "$Prefix Dana" -UserPrincipalName "$Prefix-dana@$Domain" `
    -MailNickname "$Prefix-dana" -AccountEnabled -PasswordProfile $pw

# Two security groups: Dana is in INNER, and INNER is a member of OUTER.
$outer = New-MgGroup -DisplayName "$Prefix-outer" -MailEnabled:$false -MailNickname "$Prefix-outer" -SecurityEnabled
$inner = New-MgGroup -DisplayName "$Prefix-inner" -MailEnabled:$false -MailNickname "$Prefix-inner" -SecurityEnabled
New-MgGroupMember -GroupId $inner.Id -DirectoryObjectId $dana.Id
New-MgGroupMember -GroupId $outer.Id -DirectoryObjectId $inner.Id
```

Dana is **not** a direct member of `outer`. Remember that for Part 4.

## Part 2 - Read the built-in roles

```powershell
# How many built-in roles exist today
(Get-AzRoleDefinition | Where-Object IsCustom -eq $false).Count

# The five fundamental roles, side by side
'Owner','Contributor','Reader','User Access Administrator','Role Based Access Control Administrator' |
    ForEach-Object { Get-AzRoleDefinition -Name $_ } |
    Select-Object Name, Id, @{ n = 'Actions'; e = { $_.Actions -join ', ' } },
                  @{ n = 'NotActions'; e = { $_.NotActions.Count } },
                  @{ n = 'DataActions'; e = { $_.DataActions.Count } }

# What Contributor can't do
(Get-AzRoleDefinition -Name 'Contributor').NotActions
```

Answer from the output before reading on:

1. Which of the five has `DataActions`? None, which is why none of them reads blob data.
2. Which `NotActions` stop a Contributor from assigning roles *and* assigning policies?
3. What does Role Based Access Control Administrator have that Reader doesn't?

In the portal: any scope > **Access control (IAM)** > **Roles**. Search for Contributor
and open **View** > **Permissions** to see the same lists.

## Part 3 - Assign at two scopes

Two assignments, deliberately at different scopes and through different paths:

| Principal | Role | Scope | Path to Dana |
| --- | --- | --- | --- |
| `az104-01-02-outer` (group) | Reader | Subscription | Nested group: outer contains inner contains Dana |
| Dana (user) | Contributor | `rg-az104-lab-01-02` | Direct |

### Method A - Portal

1. **Subscriptions** > your lab subscription > **Access control (IAM)** > **Add** >
   **Add role assignment**. **Job function roles** > **Reader** > **Next** > **Members**:
   select `az104-01-02-outer` > **Review + assign**.
2. **Resource groups** > `rg-az104-lab-01-02` > **Access control (IAM)** > **Add** >
   **Add role assignment**. **Privileged administrator roles** > **Contributor** >
   **Members**: select `az104-01-02 Dana` > **Review + assign**.

### Method B - PowerShell

```powershell
New-AzRoleAssignment -ObjectId $outer.Id -RoleDefinitionName 'Reader' -Scope "/subscriptions/$SubId"
New-AzRoleAssignment -ObjectId $dana.Id  -RoleDefinitionName 'Contributor' -ResourceGroupName $Rg
```

### Method C - Azure CLI

```bash
az role assignment create --assignee "<outer-group-object-id>" --role "Reader" \
  --scope "/subscriptions/<subscription-id>"
az role assignment create --assignee "<dana-object-id>" --role "Contributor" \
  --scope "/subscriptions/<subscription-id>/resourceGroups/rg-az104-lab-01-02"
```

Changes can take up to 10 minutes to take effect.

## Part 4 - Test as Dana

Sign in to the Azure portal as Dana in a private browser window. Set the permanent
password, and expect a prompt to register for multifactor authentication.

1. **Resource groups**: Dana sees **every** resource group, including `rg-az104-core`.
   That's the subscription Reader assignment, reaching her through **two levels of group
   nesting**. Azure RBAC group assignments are transitive. Compare that with 01-01, where
   group-based licensing stops at the first level.
2. On `rg-az104-lab-01-02` > **Tags**, add `tested = yes` and apply. It succeeds:
   Contributor at that scope.
3. On `rg-az104-core` > **Tags**, try the same. It fails: only Reader applies there.
4. On `rg-az104-lab-01-02` > **Access control (IAM)** > **Add role assignment**. Dana
   can't create one: Contributor excludes `Microsoft.Authorization/*/Write`.

Sign Dana out.

## Part 5 - Interpret the assignments

As yourself, not Dana.

**Check access.** `rg-az104-lab-01-02` > **Access control (IAM)** > **Check access** >
select Dana. Two assignments appear: Contributor at this scope, and Reader **inherited**
from the subscription through a group. Then run Check access at the **subscription**:
only Reader appears, because Check access never lists child-scope assignments.

**The CLI's defaults.** Run each command and compare what comes back:

```bash
az role assignment list --assignee "<dana-upn>" -o table
az role assignment list --assignee "<dana-upn>" --all -o table
az role assignment list --assignee "<dana-upn>" --all --include-inherited --include-groups \
  --query "[].{role:roleDefinitionName, scope:scope, via:principalName}" -o table
```

The first shows nothing: Dana's only direct assignment is below subscription scope. The
second finds Contributor. Only the third shows everything Dana can actually do.

```powershell
Get-AzRoleAssignment -SignInName "$Prefix-dana@$Domain" -ExpandPrincipalGroups |
    Select-Object RoleDefinitionName, Scope, DisplayName, ObjectType
```

**Deny assignments.** Open the **Deny assignments** tab at the subscription. It is almost
certainly empty. You can't create one here; Azure does, for example for a deployment
stack with deny settings.

## Part 6 - Remove one path, keep the other

```powershell
Remove-AzRoleAssignment -ObjectId $dana.Id -RoleDefinitionName 'Contributor' -ResourceGroupName $Rg
```

Wait, or sign Dana out and back in, then test Part 4 step 2 again. The tag edit now fails,
yet Dana **still sees** `rg-az104-lab-01-02`. Removing her direct assignment didn't remove
the Reader she inherits through a group at a higher scope. That is the scenario behind
"the user still has access after the assignment was removed".

## Validation

```powershell
# 1. Dana's effective assignments: Reader at subscription scope, via a group
Get-AzRoleAssignment -SignInName "$Prefix-dana@$Domain" -ExpandPrincipalGroups |
    Select-Object RoleDefinitionName, Scope, DisplayName

# 2. The nesting that makes it reach her
Get-MgGroupMember -GroupId $outer.Id | ForEach-Object { $_.AdditionalProperties.displayName }

# 3. No direct Contributor remains on the lab resource group (Part 6)
Get-AzRoleAssignment -ResourceGroupName $Rg -ObjectId $dana.Id   # expect nothing
```

### Portal validation

- **Check access** for Dana at `rg-az104-lab-01-02` shows only the inherited Reader.
- The subscription's **Access control (IAM)** > **Role assignments** shows Reader for
  `az104-01-02-outer`.

## What just happened?

You saw the three parts of every assignment: **who** (a user or a group), **what** (a role definition) and **where** (a scope). Access granted at the subscription **inherited** down to the resource group, and the group nesting carried it to Dana without her ever being named in an assignment. Removing the direct Contributor path left the inherited Reader path untouched: access is the union of every path, so you take it away one path at a time.

## Teardown

### 1. Resources

```powershell
Remove-AzResourceGroup -Name $Rg -Force
```

### 2. Subscription scope

The Reader assignment at subscription scope is not in any resource group. Remove it
explicitly, then confirm nothing for this lab remains:

```powershell
Remove-AzRoleAssignment -ObjectId $outer.Id -RoleDefinitionName 'Reader' -Scope "/subscriptions/$SubId"

Get-AzRoleAssignment |
    Where-Object { $_.DisplayName -like "$Prefix*" -or -not $_.DisplayName } |
    Select-Object RoleDefinitionName, DisplayName, Scope      # expect nothing
```

Delete the role assignment **before** deleting the group. If you delete the group first,
the assignment remains as an orphan with an unresolved principal.

### 3. Directory scope

```powershell
Get-MgGroup -Filter "startsWith(displayName,'$Prefix')" | ForEach-Object { Remove-MgGroup -GroupId $_.Id }
Get-MgUser  -Filter "startsWith(displayName,'$Prefix')" | ForEach-Object { Remove-MgUser  -UserId  $_.Id }
```

### 4. Soft-deleted remains

Dana stays under **Users** > **Deleted users** for 30 days, and can be restored until then.
Delete her permanently there if you don't want her restorable.

### 5. Access

Remove any Azure or Microsoft Entra role you gave your working account only for this lab.
If you elevated access to complete the lab, turn **Access management for Azure
resources** back to **No**.

### 6. Verify

```powershell
Get-AzResourceGroup -Name $Rg -ErrorAction SilentlyContinue                 # expect nothing
Get-AzRoleAssignment |
    Where-Object { -not $_.DisplayName } | Measure-Object                    # expect 0 orphans
Get-MgGroup -Filter "startsWith(displayName,'$Prefix')" | Measure-Object     # expect 0
```

Tick these once the commands above return what's expected. The lab counts as **practised** only when the validation and teardown checklists are both complete.

- [ ] The lab resource group no longer exists.
- [ ] The orphaned role-assignment count is **0**.
- [ ] No groups with the lab prefix remain.
