# Lab 01-01 - Microsoft Entra Users and Groups

**Objective:** Manage Microsoft Entra users and groups
**Estimated cost:** Free - no Azure resources are created. Directory objects are not
billed. Parts marked **(P1)** need a Microsoft Entra ID P1-level licence in the
tenant and are optional.
**Licensing required:** Microsoft Entra ID Free for Parts 1, 2, 3 and 5. Part 4 needs
any licence to assign. Part 2b needs Entra ID P1. Part 6 needs Entra ID P1/P2 or
Microsoft 365 Business Standard or higher, for password *reset* by non-admin users.

> Complete **Module 0** first. Run this lab in a **lab tenant**, never in a
> production directory. SSPR and external collaboration settings are
> **tenant-wide**: a change affects every user, not just the lab objects.
>
> **Before you change anything, record the current values** of the settings in
> Part 5 and Part 6. Teardown puts them back, and it can only put back what you
> wrote down.

Portal steps were checked against Microsoft Learn on 2026-09-29. Portal labels
change often; if a label differs, the Microsoft Learn page linked in each part is
the reference.

## Why this matters

New staff, partners and contractors all need an identity before they can be given anything. Granting access person by person doesn't scale and can't be audited, so administrators create users with the right properties, put them in groups, and give access to the groups.

## The desired state

When you finish, these will be true. Each one is checked in **Validation** below.

- Lab users whose **properties** (department, usage location) are set, because group rules and licensing read them.
- An **assigned** security group with a known member.
- A **guest** user invited from outside the tenant, under external collaboration settings you have read and recorded.
- Optionally, with Microsoft Entra ID P1: a **dynamic** group and **self-service password reset** scoped to one group.

## Prerequisites

- Roles in Microsoft Entra ID, assigned to your working account only for this lab:
  **User Administrator** (users, groups, invitations, restore),
  **Authentication Policy Administrator** (Part 6), and **License Administrator**
  (Part 4, only if you have licences to assign). Changing external collaboration
  settings in Part 5 needs **External Identity Provider Administrator**; reading
  them doesn't.
- Microsoft Graph PowerShell: `Install-Module Microsoft.Graph -Scope CurrentUser`
- Azure CLI, optional: `az login` with the same account.
- A personal email address you control, to receive a guest invitation in Part 5.

```powershell
$LabId  = '01-01'
$Prefix = "az104-$LabId"
$Domain = '<tenant>.onmicrosoft.com'   # your tenant's initial domain
Connect-MgGraph -Scopes 'User.ReadWrite.All', 'Group.ReadWrite.All', 'User.Invite.All'
# If a cmdlet reports insufficient privileges, ask it what it needs:
#   Find-MgGraphCommand -Command Get-MgSubscribedSku | Select-Object -ExpandProperty Permissions
```

Every object you create is named `az104-01-01-...`, so teardown can find them all.

## Part 1 - Create users

### Method A - Portal

1. Microsoft Entra admin center > **Entra ID** > **Users** > **All users** >
   **New user** > **Create new user**.
2. User principal name `az104-01-01-avery`, display name `az104-01-01 Avery`.
   Let the portal generate a password and copy it.
3. On **Properties**, set **Department** to `Sales` and **Usage location** to your
   country. Create the user.

### Method B - PowerShell

```powershell
$pw = @{ Password = '<temporary-password>'; ForceChangePasswordNextSignIn = $true }
$blake = New-MgUser -DisplayName "$Prefix Blake" `
    -UserPrincipalName "$Prefix-blake@$Domain" -MailNickname "$Prefix-blake" `
    -AccountEnabled -PasswordProfile $pw -Department 'Finance'
# Deliberately NO -UsageLocation. Part 4 uses this user to show why that matters.
```

### Method C - Azure CLI

```bash
az ad user create \
  --display-name "az104-01-01 Casey" \
  --user-principal-name "az104-01-01-casey@<tenant>.onmicrosoft.com" \
  --password "<temporary-password>"
```

## Part 2 - Groups

### 2a. Assigned security group

```powershell
$sales = New-MgGroup -DisplayName "$Prefix-sales-assigned" -MailEnabled:$false `
    -MailNickname "$Prefix-sales-assigned" -SecurityEnabled
$avery = Get-MgUser -Filter "startsWith(displayName,'$Prefix Avery')"
New-MgGroupMember -GroupId $sales.Id -DirectoryObjectId $avery.Id
```

Portal equivalent: **Entra ID** > **Groups** > **All groups** > **New group**, group
type **Security**, membership type **Assigned**, then add Avery under **Members**.

### 2b. (P1) Dynamic user group

```powershell
$dyn = New-MgGroup -DisplayName "$Prefix-sales-dynamic" -MailEnabled:$false `
    -MailNickname "$Prefix-sales-dynamic" -SecurityEnabled `
    -GroupTypes 'DynamicMembership' `
    -MembershipRule 'user.department -eq "Sales"' `
    -MembershipRuleProcessingState 'On'
```

Then prove the two rules from the lesson:

1. Open the dynamic group in the portal and try to add Blake as a member. Manual
   membership changes aren't allowed on a dynamic group; note how the portal tells you.
2. Change Blake's department to `Sales` (Part 3) and watch Blake appear once the
   rule is re-evaluated. Processing is not instant; refresh the Members page.

Without a P1 licence, the dynamic option is unavailable. Read the rule syntax in
the lesson and move on; nothing later depends on this part.

## Part 3 - User and group properties

```powershell
# Edit properties that rules and licensing read
Update-MgUser -UserId $blake.Id -Department 'Sales' -JobTitle 'Analyst'

# Read them back
Get-MgUser -UserId $blake.Id -Property DisplayName,Department,JobTitle,UsageLocation |
    Select-Object DisplayName, Department, JobTitle, UsageLocation
```

In the portal, open a group's **Properties** and note what you can change after
creation (name, description) and what shows the choices you made at creation (group
type, membership type). Then try **Users** > **All users** > **Bulk operations** >
**Download users**. It is read-only and shows the CSV shape that the bulk create
template uses.

## Part 4 - Licences and usage location

If your tenant has no licences to assign, read this part and skip the commands.
`Get-MgSubscribedSku` returning nothing is a result in itself.

```powershell
Get-MgSubscribedSku -All | Select-Object SkuPartNumber, ConsumedUnits, SkuId

$sku = Get-MgSubscribedSku -All | Where-Object SkuPartNumber -eq '<sku-part-number>'

# Blake has no usage location (Part 1). Expect this to fail and read the error.
Set-MgUserLicense -UserId $blake.Id -AddLicenses @{ SkuId = $sku.SkuId } -RemoveLicenses @()

# Fix the cause, then assign again
Update-MgUser -UserId $blake.Id -UsageLocation '<two-letter-country-code>'
Set-MgUserLicense -UserId $blake.Id -AddLicenses @{ SkuId = $sku.SkuId } -RemoveLicenses @()
```

Group-based licensing is assigned in the **Microsoft 365 admin center** > **Billing**
> **Licenses** > **Assign licenses**, choosing a group. If you do it, assign to
`az104-01-01-sales-assigned` and note that only first-level members receive the
licence.

## Part 5 - External users

### 5a. Read the external collaboration settings first

**Entra ID** > **External Identities** > **External collaboration settings**.
**Write down** the current **Guest user access**, **Guest invite settings** and
**Collaboration restrictions** before you continue.

### 5b. Invite a guest

Portal: **Users** > **All users** > **New user** > **Invite external user**, using
the personal address you control. Or:

```powershell
New-MgInvitation -InvitedUserDisplayName "$Prefix Guest" `
    -InvitedUserEmailAddress '<your-personal-address>' `
    -InviteRedirectUrl 'https://myapplications.microsoft.com' -SendInvitationMessage
```

Open the new user and confirm **User type** is **Guest**. Redeem the invitation from
your personal mailbox if you want to see the consent experience.

### 5c. Prove "most restrictive wins" (optional; needs External Identity Provider Administrator)

Add a test domain you don't use (for example `fabrikam.com`) to a **deny** list
under **Collaboration restrictions**, then try to invite an address at that
domain. The invitation is refused. Remove the entry straight away.

## Part 6 - (P1) Self-service password reset

1. Create an assigned security group `az104-01-01-sspr-pilot` and add **Avery only**.
   Avery holds no admin role. That's the point.
2. **Entra ID** > **Password reset** > **Properties**. **Write down** the current
   value. Then set **Self service password reset enabled** to **Selected** and choose
   `az104-01-01-sspr-pilot`. Note that only one group can be chosen.
3. Review **Authentication methods** (number of methods required) and
   **Registration**. Methods themselves are managed in the Authentication methods
   policy.
4. In a private browser window, sign in as Avery at `https://aka.ms/ssprsetup` and
   register, then reset Avery's password at `https://aka.ms/sspr`.
5. Try the same reset flow with your own administrator account and compare. It asks
   for two methods regardless of the policy you just set: the fixed two-gate
   administrator policy.

## Validation

```powershell
# 1. Users exist with the properties rules and licensing depend on
Get-MgUser -Filter "startsWith(displayName,'$Prefix')" `
    -Property DisplayName,UserType,Department,UsageLocation |
    Select-Object DisplayName, UserType, Department, UsageLocation

# 2. The assigned group holds Avery
Get-MgGroupMember -GroupId $sales.Id | ForEach-Object { $_.AdditionalProperties.displayName }

# 3. (P1) The dynamic group holds everyone whose department is Sales, and nobody else
Get-MgGroupMember -GroupId $dyn.Id | ForEach-Object { $_.AdditionalProperties.displayName }

# 4. The guest is a guest
Get-MgUser -Filter "userType eq 'Guest'" -Property DisplayName,UserType |
    Where-Object DisplayName -like "$Prefix*" | Select-Object DisplayName, UserType
```

### Portal validation

- **Groups** > `az104-01-01-sales-dynamic` > **Dynamic membership rules** shows your
  rule, and its members can't be edited by hand.
- **Password reset** > **Properties** shows **Selected** with one group (Part 6 only).
- **External collaboration settings** match what you wrote down in 5a.

## What just happened?

Every object you created lives in the **Microsoft Entra tenant**, not in the subscription. That's why none of it appeared in a resource group, and why deleting a resource group won't remove it. The properties you set aren't decoration: usage location is required before a licence can be assigned, and department is what a dynamic rule reads. The guest is a full directory object with a different **user type**, which is how the tenant tells members and external users apart.

## Teardown

Everything here is in the directory, not in a resource group, so deleting a resource
group removes none of it. Work through all six buckets.

### 1. Resources

None. This lab creates no Azure resources. Confirm:

```powershell
Get-AzResource -TagName 'az104-module' -TagValue '01-01'   # expect nothing
```

### 2. Subscription scope

None. No role assignments, policies or locks are created at subscription scope.

### 3. Directory scope

```powershell
# Remove any licence you assigned in Part 4 first, so it's freed immediately
# Set-MgUserLicense -UserId $blake.Id -AddLicenses @() -RemoveLicenses @($sku.SkuId)

Get-MgGroup -Filter "startsWith(displayName,'$Prefix')" | ForEach-Object { Remove-MgGroup -GroupId $_.Id }
Get-MgUser  -Filter "startsWith(displayName,'$Prefix')" | ForEach-Object { Remove-MgUser  -UserId  $_.Id }
```

Then put back the tenant-wide settings you recorded:

- **Password reset** > **Properties**: restore the value from Part 6 step 2.
- **External collaboration settings**: restore the values from Part 5a, and confirm
  no test domain remains in the deny list.

### 4. Soft-deleted remains

Deleted users stay under **Users** > **Deleted users** for 30 days and keep their
user principal names reserved. To release them now, select each `az104-01-01` user
there and choose **Delete permanently**. That can't be undone, which is why it is a
deliberate step and not part of the script.

### 5. Access

Remove the Entra roles you assigned to your working account for this lab: User
Administrator, Authentication Policy Administrator, License Administrator and
External Identity Provider Administrator, if you added them. A lab that leaves
standing admin roles behind has created the kind of over-privileged access that
module 01-02 teaches you to find.

### 6. Verify

```powershell
Get-MgUser  -Filter "startsWith(displayName,'$Prefix')" | Measure-Object   # expect 0
Get-MgGroup -Filter "startsWith(displayName,'$Prefix')" | Measure-Object   # expect 0
```

Tick these once the commands above return what's expected. The lab counts as **practised** only when the validation and teardown checklists are both complete.

- [ ] `Get-MgUser` with the lab prefix returns **0**.
- [ ] `Get-MgGroup` with the lab prefix returns **0**.
