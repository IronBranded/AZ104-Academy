## Why this matters

Access control decides who may act. It doesn't decide what's allowed to exist, protect a production resource from its own Owner, or tell you who owns a resource and what it costs. Governance controls do, and they're applied to the same hierarchy of scopes.

## The desired state

When you finish, these will be true. Each one is checked in **Validation** below.

- A **policy** that found non-compliant existing resources and fixed them with a **remediation task**.
- A **policy** that blocked a request outright.
- A **ReadOnly lock** that stopped even an Owner.
- A **management group** you created, used and removed, and a read-only tour of **costs and Advisor**.

## Prerequisites

- **Owner** on the lab subscription. Locks need `Microsoft.Authorization/locks/*`, policy
  assignments need `Microsoft.Authorization` write access, and the policy's remediation
  identity needs a role granted to it. Contributor has none of these.
- Azure PowerShell (`Az.Resources`, `Az.PolicyInsights`, `Az.Network`) or the Azure CLI.

```powershell
$LabId  = '01-03'
$Prefix = "az104-$LabId"
$Loc    = '<region>'             # the region you normally use
$OtherLoc = '<different-region>' # any other region, used to trigger a deny
$Rg     = "rg-az104-lab-$LabId"
$RgT    = "rg-az104-lab-$LabId-target"
Connect-AzAccount
$SubId  = (Get-AzContext).Subscription.Id
```

## Part 1 - Setup: tags don't inherit

```powershell
New-AzResourceGroup -Name $Rg  -Location $Loc -Tag @{ 'az104-module' = $LabId; CostCenter = '1234' }
New-AzResourceGroup -Name $RgT -Location $Loc -Tag @{ 'az104-module' = $LabId }

$vnet = New-AzVirtualNetwork -Name "vnet-$Prefix" -ResourceGroupName $Rg -Location $Loc `
    -AddressPrefix '10.13.0.0/16'
$vnet.Tag     # empty: the resource group's CostCenter tag was NOT inherited
```

## Part 2 - Azure Policy: fix existing resources with remediation

Assign the built-in **Inherit a tag from the resource group** (effect `modify`) to
`rg-az104-lab-01-03`.

1. **Policy** > **Assignments** > **Assign policy**. Set **Scope** to the lab resource group.
   For **Policy definition**, search for *Inherit a tag from the resource group* and pick the
   one **without** "if missing".
2. **Parameters**: **Tag Name** = `CostCenter`.
3. **Remediation**: keep the **system-assigned managed identity**. The portal grants it the
   roles the definition needs. Leave **Create a remediation task** clear for now.
4. **Review + create**.

The virtual network already exists, so the assignment won't change it. Wait about 5 minutes
for the assignment to apply, then force an evaluation:

```powershell
Start-AzPolicyComplianceScan -ResourceGroupName $Rg
Get-AzPolicyState -ResourceGroupName $Rg |
    Select-Object ResourceId, PolicyDefinitionAction, ComplianceState
```

The virtual network shows as **NonCompliant**. Now remediate it: **Policy** > **Remediation** >
**Policies to remediate** > your assignment > **Remediate**. When the task finishes, check the
tag:

```powershell
(Get-AzVirtualNetwork -Name "vnet-$Prefix" -ResourceGroupName $Rg).Tag   # CostCenter = 1234
```

Resources created from now on in this resource group get the tag at request time, without a
remediation task.

## Part 3 - A policy that blocks a move

Assign **Allowed locations** (`deny`) to the **target** resource group, allowing only
`$OtherLoc`, a region your virtual network is **not** in:

```powershell
$allowed = Get-AzPolicyDefinition | Where-Object { $_.DisplayName -eq 'Allowed locations' }
New-AzPolicyAssignment -Name "$Prefix-allowed-loc" -PolicyDefinition $allowed `
    -Scope (Get-AzResourceGroup -Name $RgT).ResourceId `
    -PolicyParameterObject @{ listOfAllowedLocations = @($OtherLoc) }
```

Wait about 5 minutes, then try to move the virtual network into the target group:

```powershell
$vnetId = (Get-AzVirtualNetwork -Name "vnet-$Prefix" -ResourceGroupName $Rg).Id
Move-AzResource -DestinationResourceGroupName $RgT -ResourceId $vnetId -Force
```

The move is refused with **RequestDisallowedByPolicy**: Resource Manager validates the move
against policies at the target. Remove the assignment, wait a few minutes, and move again:

```powershell
Remove-AzPolicyAssignment -Name "$Prefix-allowed-loc" -Scope (Get-AzResourceGroup -Name $RgT).ResourceId
Move-AzResource -DestinationResourceGroupName $RgT -ResourceId $vnetId -Force

(Get-AzVirtualNetwork -Name "vnet-$Prefix" -ResourceGroupName $RgT).Id   # a different resource ID
```

Compare the two IDs: the resource group segment changed, the region didn't. The `CostCenter`
tag moved with the resource because it's on the resource. The policy on the old resource group
**doesn't** apply any more.

## Part 4 - Locks stop the Owner

```powershell
New-AzResourceLock -LockName "$Prefix-nodelete" -LockLevel CanNotDelete -ResourceGroupName $RgT -Force

# Modify works under CanNotDelete
Update-AzTag -ResourceId (Get-AzVirtualNetwork -Name "vnet-$Prefix" -ResourceGroupName $RgT).Id `
    -Tag @{ tested = 'yes' } -Operation Merge

# Delete fails, for the resource and for its resource group, even though you are Owner
Remove-AzVirtualNetwork -Name "vnet-$Prefix" -ResourceGroupName $RgT -Force
Remove-AzResourceGroup -Name $RgT -Force
```

Now replace it with a **ReadOnly** lock and try the tag change again:

```powershell
$lockId = (Get-AzResourceLock -ResourceGroupName $RgT -LockName "$Prefix-nodelete").LockId
Remove-AzResourceLock -LockId $lockId -Force
New-AzResourceLock -LockName "$Prefix-readonly" -LockLevel ReadOnly -ResourceGroupName $RgT -Force

Update-AzTag -ResourceId (Get-AzVirtualNetwork -Name "vnet-$Prefix" -ResourceGroupName $RgT).Id `
    -Tag @{ tested = 'again' } -Operation Merge      # fails: ReadOnly blocks modification
```

Leave the ReadOnly lock in place for now; teardown removes it first.

## Part 5 - Exemption versus exclusion (portal)

1. Assign the built-in **Require a tag on resources** (`deny`) to the **subscription**, with
   **Tag Name** = `Owner`. On the **Basics** tab, set **Policy enforcement** to **Disabled**
   (`DoNotEnforce`). It reports, but blocks nothing, so it can't break anything else in your
   subscription.
2. On the same assignment, add an **exclusion** for `rg-az104-lab-01-03`.
3. On the assignment's compliance view, create an **exemption** for `rg-az104-lab-01-03-target`,
   category **Waiver**, expiring tomorrow.
4. After the next evaluation, compare the two resource groups in the compliance report: the
   excluded one **doesn't appear at all**, and the exempted one appears as **Exempted**.

## Part 6 - Management groups

Skip this part if your subscription's parent isn't the **Tenant root group** or a management
group you control.

1. **Management groups**: note your subscription's current parent. If you've never created one,
   you'll see **Tenant root group**, whose ID is your tenant ID.
2. Create a management group and move the subscription into it:

```powershell
New-AzManagementGroup -GroupName "$Prefix-mg" -DisplayName 'AZ-104 lab 01-03'
New-AzManagementGroupSubscription -GroupId "$Prefix-mg" -SubscriptionId $SubId
```

3. The portal can take up to 30 minutes to show the move, because the hierarchy is cached.
4. Open **Management groups** > **Settings** (hierarchy settings) and read the two options: the
   **default management group** for new subscriptions, and **require authorization** to create
   management groups. Don't change them in a shared tenant.

## Part 7 - Costs and Advisor (read-only)

1. **Advisor** > **Cost**. Note which recommendations you have, if any. A lab subscription often
   has none.
2. **Advisor** > **Configuration** > **VM/Virtual Machine Scale Sets right sizing**. Read the CPU
   utilization and lookback options. Don't change them.
3. **Cost Management** > **Cost analysis**, grouped by the tag `CostCenter`. It's empty, because
   tags appear in cost data only on resources that produce usage records, and an empty virtual
   network produces none.
4. **Subscriptions** > your subscription > **Change directory**. **Read the warning and cancel.**
   Name what it would permanently delete.

```powershell
# 2. The ReadOnly lock is present on the target resource group
Get-AzResourceLock -ResourceGroupName $RgT | Select-Object Name, @{ n = 'Level'; e = { $_.Properties.level } }

# 3. Policy assignments this lab created
Get-AzPolicyAssignment -Scope "/subscriptions/$SubId" -IncludeDescendent |
    Where-Object { $_.Scope -like "*$LabId*" -or $_.Name -like "$Prefix*" } |

```

## What just happened?

Three controls, three questions. **Policy** evaluated the resource itself, whoever sent the request, and remediation used the assignment's managed identity to change existing resources. The **lock** ignored roles completely: it applies to everyone, which is why an Owner was refused. **Tags** stayed where you put them: they don't inherit from a resource group unless a policy copies them, which is exactly what remediation did.

## Teardown

### 1. Resources

Locks first. A lock blocks every delete below it, for you too.

```powershell
Get-AzResourceLock -ResourceGroupName $RgT | ForEach-Object { Remove-AzResourceLock -LockId $_.LockId -Force }
Get-AzResourceLock -ResourceGroupName $Rg  | ForEach-Object { Remove-AzResourceLock -LockId $_.LockId -Force }
Remove-AzResourceGroup -Name $RgT -Force
Remove-AzResourceGroup -Name $Rg  -Force
```

### 2. Subscription scope

Delete the assignments from Parts 2 and 5, and the exemption, in **Policy** > **Assignments** and
**Policy** > **Exemptions**. Then find the role assignment the portal granted to the Part 2
assignment's managed identity. Deleting the policy assignment leaves it behind, with a principal
that no longer resolves:

```powershell
# No -Scope: list every assignment in the subscription, at any scope. With
# -Scope /subscriptions/..., Get-AzRoleAssignment returns only assignments at
# that scope and ABOVE, and would miss one made at resource-group scope.
Get-AzRoleAssignment |
    Where-Object { -not $_.DisplayName -or $_.ObjectType -eq 'Unknown' } |
    Select-Object RoleDefinitionName, ObjectId, Scope
# Remove each orphan created by this lab:
# Remove-AzRoleAssignment -ObjectId <id> -RoleDefinitionName <role> -Scope <scope>
```
