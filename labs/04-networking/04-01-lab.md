# Lab 04-01 - Virtual Networks

**Objective:** Configure and manage virtual networks in Azure
**Estimated cost:** Medium - four virtual networks and a route table (free), one small B-series Linux VM
**without** a public IP for about 45 minutes, and a Standard public IP that exists for a few minutes. Peering
bills for data that crosses it, and this lab sends almost none. Delete everything the same day.
**Licensing required:** None beyond an Azure subscription.

> **The VM has an hourly meter.** It's tagged for the Module 0 compute brake. Part 6 only *creates and
> deletes* a public IP; Standard public IPs bill while they exist, attached or not.

Portal steps were checked against Microsoft Learn on 2026-09-30.

## Prerequisites

- **Network Contributor** (or Contributor, or Owner) on the lab subscription.
- The Azure CLI.

```powershell
$LabId = '04-01'
$Rg    = "rg-az104-lab-$LabId"
$Loc   = '<region>'
az group create --name $Rg --location $Loc --tags az104-module=$LabId
```

## Part 1 - Virtual networks, subnets and the five reserved addresses

```powershell
# A: the network with the VM. B: a hub. C: a spoke of B. X: overlaps A on purpose.
az network vnet create -g $Rg -n vnet-a --address-prefix 10.41.0.0/16 --subnet-name web  --subnet-prefixes 10.41.1.0/24
az network vnet create -g $Rg -n vnet-b --address-prefix 10.42.0.0/16 --subnet-name hub  --subnet-prefixes 10.42.1.0/24
az network vnet create -g $Rg -n vnet-c --address-prefix 10.43.0.0/16 --subnet-name app  --subnet-prefixes 10.43.1.0/24
az network vnet create -g $Rg -n vnet-x --address-prefix 10.41.0.0/16 --subnet-name dup  --subnet-prefixes 10.41.9.0/24

# The smallest subnet is /29 ...
az network vnet subnet create -g $Rg --vnet-name vnet-a -n tiny --address-prefixes 10.41.2.0/29
# ... and /30 is refused
az network vnet subnet create -g $Rg --vnet-name vnet-a -n tinier --address-prefixes 10.41.3.0/30
```

A `/29` holds 8 addresses, but 5 are reserved (`.0`, `.1`, `.2`, `.3` and `.7`), so `tiny` can hold **3** NICs.

Check whether the `web` subnet allows default outbound access:

```powershell
az network vnet subnet show -g $Rg --vnet-name vnet-a -n web --query defaultOutboundAccess
```

`false` means it's a private subnet: the new default. An empty result means the API version your CLI used
predates the change; such a subnet still allows default outbound access.

## Part 2 - Peering: two links, overlap, and non-transitivity

```powershell
$idA = az network vnet show -g $Rg -n vnet-a --query id -o tsv
$idB = az network vnet show -g $Rg -n vnet-b --query id -o tsv
$idC = az network vnet show -g $Rg -n vnet-c --query id -o tsv
$idX = az network vnet show -g $Rg -n vnet-x --query id -o tsv

# One link only: Initiated
az network vnet peering create -g $Rg --vnet-name vnet-a -n a-to-b --remote-vnet $idB --allow-vnet-access
az network vnet peering show   -g $Rg --vnet-name vnet-a -n a-to-b --query peeringState -o tsv      # Initiated

# The reverse link: both Connected
az network vnet peering create -g $Rg --vnet-name vnet-b -n b-to-a --remote-vnet $idA --allow-vnet-access
az network vnet peering show   -g $Rg --vnet-name vnet-a -n a-to-b --query peeringState -o tsv      # Connected

# B also peers with C, both directions
az network vnet peering create -g $Rg --vnet-name vnet-b -n b-to-c --remote-vnet $idC --allow-vnet-access
az network vnet peering create -g $Rg --vnet-name vnet-c -n c-to-b --remote-vnet $idB --allow-vnet-access

# Overlapping address spaces: refused
az network vnet peering create -g $Rg --vnet-name vnet-a -n a-to-x --remote-vnet $idX --allow-vnet-access
```

## Part 3 - One VM, and its effective routes

```powershell
az vm list-skus --location $Loc --size Standard_B --query "[].name" -o tsv
$Size = '<a-small-B-series-size>'
az vm create -g $Rg -n vm-a --image Ubuntu2204 --size $Size --vnet-name vnet-a --subnet web `
  --public-ip-address '""' --nsg '""' --admin-username azureuser --generate-ssh-keys `
  --storage-sku StandardSSD_LRS --tags az104-module=$LabId

$nic = az vm show -g $Rg -n vm-a --query "networkProfile.networkInterfaces[0].id" -o tsv
az network nic show-effective-route-table --ids $nic -o table
```

Read the table:

- `10.41.0.0/16` has next hop **VnetLocal**: its own network.
- `10.42.0.0/16` has next hop **VNetPeering**: the peered hub.
- There's **no route for `10.43.0.0/16`**. A peers with B and B peers with C, but **peering isn't transitive**.
- `0.0.0.0/0` goes to **Internet** (a system route), plus some ranges with next hop **None**.

Network Watcher was enabled for the region automatically when you created the first virtual network. Look for
it under **Network Watcher**, in a resource group Azure created for it.

## Part 4 - A user-defined route, read with next hop

```powershell
az vm list-ip-addresses -g $Rg -n vm-a -o table      # note the private IP; it's usually 10.41.1.4

# Before: where does traffic to the hub go?
az network watcher show-next-hop -g $Rg --vm vm-a --source-ip <vm-private-ip> --dest-ip 10.42.1.10 -o table   # VNetPeering
```

```powershell
# A route table that drops traffic to the hub, associated with web
az network route-table create -g $Rg -n rt-web
az network route-table route create -g $Rg --route-table-name rt-web -n drop-hub `
  --address-prefix 10.42.0.0/16 --next-hop-type None
az network vnet subnet update -g $Rg --vnet-name vnet-a -n web --route-table rt-web

# After: next hop None, and the route table that decided it
az network watcher show-next-hop -g $Rg --vm vm-a --source-ip <vm-private-ip> --dest-ip 10.42.1.10 -o table
```

Now add a **more specific** route and predict the next hop for `10.42.1.10` and for `10.42.7.10`:

```powershell
az network route-table route create -g $Rg --route-table-name rt-web -n hub-subnet-via-nva `
  --address-prefix 10.42.1.0/24 --next-hop-type VirtualAppliance --next-hop-ip-address 10.41.1.100
az network watcher show-next-hop -g $Rg --vm vm-a --source-ip <vm-private-ip> --dest-ip 10.42.1.10 -o table   # VirtualAppliance
az network watcher show-next-hop -g $Rg --vm vm-a --source-ip <vm-private-ip> --dest-ip 10.42.7.10 -o table   # None
```

**Longest prefix wins:** `/24` beats `/16` for `10.42.1.10`, and only the `/16` covers `10.42.7.10`. Nothing exists at
`10.41.1.100`. A real appliance there would also need **IP forwarding** on its NIC.

Remove the association before continuing:

```powershell
az network vnet subnet update -g $Rg --vnet-name vnet-a -n web --remove routeTable
```

## Part 5 - Resize a peered network, then sync

```powershell
az network vnet update -g $Rg -n vnet-b --address-prefixes 10.42.0.0/16 10.44.0.0/16
az network vnet peering show -g $Rg --vnet-name vnet-a -n a-to-b --query "remoteAddressSpace.addressPrefixes"
az network vnet peering sync -g $Rg --vnet-name vnet-a -n a-to-b
az network vnet peering show -g $Rg --vnet-name vnet-a -n a-to-b --query "remoteAddressSpace.addressPrefixes"
```

After the sync, A's view of B includes `10.44.0.0/16`. Peering routes take a few minutes to show in effective routes.

## Part 6 - A Standard public IP (create, read, delete)

```powershell
az network public-ip create -g $Rg -n pip-az104-0401 --sku Standard --allocation-method Static
az network public-ip show   -g $Rg -n pip-az104-0401 --query "{sku:sku.name, allocation:publicIPAllocationMethod, ip:ipAddress, zones:zones}" -o table
az network public-ip delete -g $Rg -n pip-az104-0401
```

Static, and billed from this moment whether attached or not. That's why it's deleted straight away. Inbound traffic to
it would stay **closed** until an NSG allows it (04-02).

## Teardown

### 1. Resources

```powershell
az group delete --name $Rg --yes
```

This removes the VM, its disk and NIC, the four virtual networks with their peerings, and the route table.

### 2. Subscription scope

Network Watcher stays enabled for the region, in the resource group Azure created for it. It costs nothing by
itself; leave it, since other labs use it.

### 3. Directory scope

None.

### 4. Soft-deleted remains

None.

### 5. Access

Remove any role you added to your working account only for this lab.

### 6. Verify

```powershell
az group exists --name $Rg                                                     # false
az network public-ip list --query "[?name=='pip-az104-0401'].name" -o tsv      # nothing
```

Then mark teardown as confirmed in the Academy.
