# Lab 04-02 - Secure Access to Virtual Networks

**Objective:** Configure secure access to virtual networks
**Estimated cost:** Medium - one small B-series Linux VM **without** a public IP for about 45 minutes, an empty
storage account, and a private endpoint (billed hourly) for about 15 minutes. **Bastion Developer is free.**
Dedicated Bastion SKUs bill from the moment they're deployed, so they're a walkthrough here. Delete everything
the same day.
**Licensing required:** None beyond an Azure subscription.

> Complete **04-01** first. **Choose a region where Bastion Developer is available** (the lesson's Sources link
> the list). The parts run in a deliberate order: you use Bastion **before** any NSG exists, so a missing
> NSG rule can't lock you out. NSG behaviour is then tested with IP flow verify and effective rules, which
> don't need a session.

Portal steps were checked against Microsoft Learn on 2026-10-01.

## Prerequisites

- **Contributor** or **Owner** on the lab subscription.
- The Azure CLI.

```powershell
$LabId = '04-02'
$Rg    = "rg-az104-lab-$LabId"
$Loc   = '<region-with-Bastion-Developer>'
$n     = Get-Random -Maximum 99999
$Sa    = "az104lab0402$n"
az group create --name $Rg --location $Loc --tags az104-module=$LabId

az network vnet create --name vnet-az104-0402 --resource-group $Rg --address-prefix 10.42.0.0/16 `
  --subnet-name web --subnet-prefixes 10.42.1.0/24
az network vnet subnet create --name endpoints --vnet-name vnet-az104-0402 --resource-group $Rg --address-prefixes 10.42.2.0/24

az storage account create --name $Sa --resource-group $Rg --location $Loc --sku Standard_LRS --kind StorageV2 --tags az104-module=$LabId
```

## Part 1 - A VM with no public IP and no NSG

```powershell
az vm create --resource-group $Rg --name vm-az104-0402 --image Ubuntu2204 --size '<a-small-B-series-size>' `
  --vnet-name vnet-az104-0402 --subnet web --public-ip-address '""' --nsg '""' `
  --admin-username azureuser --authentication-type password --tags az104-module=$LabId
# The CLI prompts for a password. Note it: Bastion asks for it in Part 2.
```

No public IP and no NSG: nothing on the internet can reach this VM, and nothing filters traffic inside the VNet.

## Part 2 - Bastion Developer (free)

1. Portal: open `vm-az104-0402` > **Connect** > **Bastion**. If you see a choice of SKUs, choose **Developer**. It
   deploys on first connection, with no AzureBastionSubnet and no public IP.
2. Authentication **Password**, user `azureuser`, **Connect**. An SSH session opens in the browser over port 443.
3. In the session:

```bash
nslookup <your-storage-account>.blob.core.windows.net
```

   Note the answer: a **public** IP address. Keep the session open for Parts 3 and 4.

Then open the VNet's **Bastion** page and read the **SKU** comparison: Developer connects to one VM at a time and
doesn't support peering. **Don't** upgrade: every dedicated SKU bills hourly from deployment.

## Part 3 - Service endpoint: same DNS, different source

```powershell
az network vnet subnet update --vnet-name vnet-az104-0402 --name web --resource-group $Rg --service-endpoints Microsoft.Storage
az storage account network-rule add --account-name $Sa --resource-group $Rg --vnet-name vnet-az104-0402 --subnet web
az storage account update --name $Sa --resource-group $Rg --default-action Deny
```

Back in the Bastion session, run the same `nslookup`. **The answer hasn't changed**: a service endpoint changes the
**source** address of the subnet's traffic, not the destination. The account is now restricted to that subnet, but
its endpoint is still public.

## Part 4 - Private endpoint: a private IP, by name

```powershell
$saId = az storage account show --name $Sa --resource-group $Rg --query id -o tsv
az network private-endpoint create --name pe-az104-0402 --resource-group $Rg --vnet-name vnet-az104-0402 --subnet endpoints `
  --private-connection-resource-id $saId --group-id blob --connection-name pe-az104-0402-conn

az network private-dns zone create --name privatelink.blob.core.windows.net --resource-group $Rg
az network private-dns link vnet create --zone-name privatelink.blob.core.windows.net --resource-group $Rg `
  --name link-0402 --virtual-network vnet-az104-0402 --registration-enabled false
az network private-endpoint dns-zone-group create --endpoint-name pe-az104-0402 --resource-group $Rg `
  --name default --private-dns-zone privatelink.blob.core.windows.net --zone-name blob
```

In the Bastion session, run `nslookup` once more. Now the same name resolves through `privatelink.blob.core.windows.net`
to a **10.42.2.x** address. Clients use the normal name; DNS does the work.

With a private endpoint in place, the public endpoint can be switched off entirely:

```powershell
az storage account update --name $Sa --resource-group $Rg --public-network-access Disabled
```

From **your own computer**, the storage account's data is now unreachable. Inside the VNet, it's reached privately.
Close the Bastion session.

**Delete the private endpoint now**; it bills hourly:

```powershell
az network private-endpoint delete --name pe-az104-0402 --resource-group $Rg
```

## Part 5 - NSGs and an application security group

```powershell
# An ASG for the web role, with the VM's NIC in it
az network asg create --name asg-web --resource-group $Rg
$nic = az vm show -g $Rg -n vm-az104-0402 --query "networkProfile.networkInterfaces[0].id" -o tsv
$nicName = ($nic -split '/')[-1]
az network nic ip-config update --nic-name $nicName --name ipconfig1 --resource-group $Rg --application-security-groups asg-web

# Subnet NSG: allow HTTPS from the internet to the web role
az network nsg create --name nsg-subnet --resource-group $Rg
az network nsg rule create --nsg-name nsg-subnet --resource-group $Rg --name allow-https-web --priority 100 `
  --direction Inbound --access Allow --protocol Tcp --source-address-prefixes Internet `
  --destination-asgs asg-web --destination-port-ranges 443
az network vnet subnet update --vnet-name vnet-az104-0402 --name web --resource-group $Rg --network-security-group nsg-subnet

# NIC NSG: no custom rules, so its defaults apply, including DenyAllInBound
az network nsg create --name nsg-nic --resource-group $Rg
az network nic update --name $nicName --resource-group $Rg --network-security-group nsg-nic
```

**Predict** whether HTTPS from the internet reaches the VM, then let Network Watcher decide:

```powershell
$ip = az vm list-ip-addresses -g $Rg -n vm-az104-0402 --query "[0].virtualMachine.network.privateIpAddresses[0]" -o tsv
az network watcher test-ip-flow --vm vm-az104-0402 --resource-group $Rg --direction Inbound `
  --protocol TCP --local "${ip}:443" --remote 203.0.113.10:50000
```

**Denied**, by `nsg-nic`'s **DenyAllInBound**. The subnet NSG allowed it, but inbound traffic must pass **both**
NSGs. Add the allow on the NIC NSG too, and test again:

```powershell
az network nsg rule create --nsg-name nsg-nic --resource-group $Rg --name allow-https-web --priority 100 `
  --direction Inbound --access Allow --protocol Tcp --source-address-prefixes Internet `
  --destination-asgs asg-web --destination-port-ranges 443
az network watcher test-ip-flow --vm vm-az104-0402 --resource-group $Rg --direction Inbound `
  --protocol TCP --local "${ip}:443" --remote 203.0.113.10:50000           # Allowed
```

## Part 6 - Effective security rules

```powershell
az network nic list-effective-nsg --name $nicName --resource-group $Rg
```

Or in the portal: the VM's NIC > **Effective security rules**. You see **both** NSGs, each with your rule and the six
default rules, with service tags expanded into address prefixes. That combined view is the reliable way to answer
"what actually applies to this VM?"

Deallocate the VM as soon as you've read it:

```powershell
az vm deallocate -g $Rg -n vm-az104-0402
```

## Validation

```powershell
az network vnet subnet show --vnet-name vnet-az104-0402 -n web -g $Rg `
  --query "{nsg:networkSecurityGroup.id, endpoints:serviceEndpoints[].service}" -o json
az network nsg rule list --nsg-name nsg-nic -g $Rg --query "[].{name:name, priority:priority, access:access}" -o table
az storage account show --name $Sa -g $Rg --query "{publicNetworkAccess:publicNetworkAccess}" -o table   # Disabled
az network private-endpoint list -g $Rg -o table                                                         # nothing: deleted
```

## Teardown

### 1. Resources

```powershell
az group delete --name $Rg --yes
```

This removes the VM, its disk and NIC, the NSGs, the ASG, the storage account, the private DNS zone and its link,
and the virtual network. If you didn't delete the private endpoint in Part 4, this removes it too.

### 2. Subscription scope

None.

### 3. Directory scope

None.

### 4. Soft-deleted remains

None.

### 5. Access

Remove any role you added to your working account only for this lab. Bastion Developer leaves nothing billable
behind.

### 6. Verify

```powershell
az group exists --name $Rg                                                        # false
az network private-endpoint list --query "[?contains(name,'az104-0402')].name" -o tsv   # nothing
```

Then mark teardown as confirmed in the Academy.
